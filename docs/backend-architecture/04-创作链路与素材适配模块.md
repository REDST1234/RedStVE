# 批次 4：创作链路与素材适配模块

## 4.1 模块职责

创作链路是拆解链路的镜像对称面。拆解链路将样例视频"打碎"为结构模板；创作链路则将用户素材"填入"模板槽位，输出可编排的视频方案。

核心职责：
- 管理**创作项目（Creation Project）**，支持用户上传多类型素材（视频/图片/文本）
- 对上传素材执行**三层资产解析（Asset Profiling）**，产出标准化的资产档案
- LLM 执行**模板槽位匹配（Slot Matching）**，判断素材能否覆盖模板各段落的需求
- 对不匹配的槽位，按**策略优先级梯队**自动调度 FFmpeg 处理或 AIGC 补全
- 输出最终的**编排时间线（Composition Timeline）**，供前端可视化与成片渲染

## 4.2 创作链路全景流程

```
用户新建创作项目
        │
        ▼
上传素材（视频/图片/文本）──► 素材入库 + 异步触发资产解析
        │
        ▼
绑定/选择结构模板（从拆解链路产出的模板库中选取）
        │
        ▼
LLM 槽位匹配分析（Asset ↔ Template Segment Matching）
        │
        ├── 完全匹配 ──► 直接编排
        │
        ├── 部分匹配 ──► 进入素材适配处理链
        │   │
        │   ├── 策略梯队 L1：FFmpeg 物理变换（裁切/变速/画幅归一化）
        │   ├── 策略梯队 L2：FFmpeg 动效伪装（Ken Burns/循环拼接）
        │   ├── 策略梯队 L3：声学处理（静音/闪避混音）
        │   └── 策略梯队 L4：AIGC 生成补全（仅当 L1-L3 无法覆盖时）
        │
        └── 完全缺失 ──► 标记缺口 + AIGC 兜底 + 结构重排建议
                │
                ▼
        编排时间线生成（Composition Timeline）
                │
                ▼
        前端可视化展示 + 用户微调 + 成片导出
```

## 4.4 三层资产档案协议（Asset Profile Protocol）

### 4.4.4 三类素材的差异化处理流程

为了将非标准化的用户输入统一收敛为标准的三层资产档案，Java 中台针对不同 `assetType` 设计了差异化的异步解析管线（Pipeline）：

#### 1. 视频素材 (VIDEO) 处理流程
视频是信息密度最高的资产，处理管线最长，旨在提取时空双重维度的特征：
1. **物理探测 (Layer 1)**：实行**两阶段极速扫描策略**。
   - **阶段一（极速预判，耗时 < 100ms）**：运行 `ffmpeg -i input.mp4 -r 1 -vf "signalstats" -f null -`。这是一次极低 CPU 开销的扫描，直接吐出全片的亮度均值（YAVG）。如果均值在正常区间 `[0.15, 0.85]`，直接写入 Layer 1 并结束任务。
   - **阶段二（模型精析，仅触发一次）**：只有当阶段一发现“均值异常”（如 `< 0.1` 或 `> 0.9`）时，才调用 Doubao 多模态模型进行“二次诊断”。让模型判断：“这是艺术化的低调摄影，还是拍摄事故（欠曝）？”
2. **场景切割 (Layer 3 预处理)**：使用算法按画面像素突变率（如 `threshold=0.4`）将长视频切分为多个物理连续的微镜头（Shots），确立坚如磐石的 `timeAnchor`。
3. **关键帧抽取与预取样缓存**：为解决前端预览性能与大模型 Token 开销，系统引入**宫格拼图法 (Grid Sequence)**。
   - 利用 FFmpeg 的 `drawtext` 在每秒抽取的关键帧上烧录鲜黄色的时序时间戳。
   - 使用 `scale & pad` 强制将任意比例单帧等比缩放并填充黑边至固定容器（如 512x512）。
   - 最后使用 `tile` 滤镜拼接为宫格大图（如 16:9 使用 2x4，9:16 使用 4x2 行列排布，确保最终图片接近 1:1）。
   - 这张极轻量的宫格图将被强缓存到 Redis 中供前端预览，**严禁在用户预览时实时调用 FFmpeg 读视频**。
4. **音频分离与 ASR (有声素材专享)**：若探测到 `hasAudio: true`，并行调用 FFmpeg 极速分离音频流，并送入 ASR 服务提取带有时间戳的字幕文本（如 SRT）。
5. **视听交叉打标 (Layer 2 & 3)**：将带有时间戳的**宫格拼图**，与**ASR 语音文稿**同时喂给 **Doubao 多模态大模型**。大模型通过交叉比对图上的视觉时间戳与 ASR 的音频时间戳，实现视听共振分析。精准输出全局风格（含 `audioVibe`）、区间 `usabilityScore`、空间锚点坐标，并将核心台词作为 `spokenText` 刻入高光片段。

#### 2. 图片素材 (IMAGE) 处理流程
图片本质上是“时间维度静止”的视频，其核心解析目标是空间识别，为后续的“动效伪装”做准备：
1. **物理探测 (Layer 1)**：读取图片宽高比、分辨率。
2. **语义感知 (Layer 2)**：调用 **Doubao 多模态大模型**识别图片中的实体物品、画风氛围，以及推测其适合在视频中扮演的段落角色（如“适合做片尾定帧”）。
3. **空间锚定 (Layer 3)**：图片没有 `timeAnchor`，但极度依赖 `spatialAnchor`。系统强制要求模型框选出核心展示主体的位置。在随后的策略梯队中，程序将结合 `KEN_BURNS_MOTION` (缓慢推拉摇移) 策略，沿着这个主体坐标将静态图片“变活”成一段 3~5 秒的动态伪视频片段。

#### 3. 文本素材 (TEXT) 处理流程
文本资产通常作为视频的包装字幕、大字报、口播旁白或提示词原材料：
1. **物理探测 (Layer 1)**：计算字数、段落结构、长短句分布。
2. **语义提纯 (Layer 2)**：利用大语言模型对长文本进行功能分类与提纯。模型需精准识别出：哪些词句是“吸睛钩子”（适合片头），哪些是“卖点陈述”（适合主体展示），哪些是“行动号召 CTA”（适合片尾）。
3. **资产降维归宿 (Layer 3)**：文本本身不具备视觉画面，它不参与视频画面的物理裁剪。它的核心作用是在后续 LLM 槽位匹配时，作为 `text_overlay`（贴纸字幕）的填充物，或者在 L4 策略梯队中作为 AIGC 的 Prompt 输入（如生成 TTS 语音或背景图）。

## 4.5 LLM 槽位匹配协议（Slot Matching Protocol）

### 输入

LLM 接收两份数据：
1. **模板快照**：`video-structure-template/v2` 的完整 JSON（含 segments/shots/rhythm）
2. **素材档案池**：所有已完成 Profiling 的素材的三层档案数组

> [!NOTE]
> **素材数量硬上限机制**：为了避免“素材档案池”体量击穿大模型的 Context Token 上限，同时保证匹配性能，系统在入口处施加硬性限制：每个创作项目**最多允许上传 1 个视频、3 张图片、3 段文本**。通过数量收口，将匹配链路的 Token 消耗稳稳控制在安全范围内。

### 输出

LLM 返回一个匹配决策 JSON：

## 4.6 素材适配策略梯队（Strategy Chain）

Java 中台接收 LLM 的 `adaptationPlan`，按照策略链顺序调度 FFmpeg 或 AIGC 接口。

### 策略优先级梯队

```
┌─────────────────────────────────────────────────────┐
│  L1: 物理变换（成本最低，效果确定）                    │
│  ├── TRIM_AND_CUT      绝对时间轴裁切                │
│  ├── SMART_CROP         居中/智能裁剪                 │
│  └── SCALE_AND_BLUR_PAD 等比缩放+模糊填充             │
├─────────────────────────────────────────────────────┤
│  L2: 时间流控（素材时长不足/过长时）                    │
│  ├── SPEED_RAMP         变速抽插帧                    │
│  └── LOOP_SEQUENCE      无缝循环兜底                  │
├─────────────────────────────────────────────────────┤
│  L3: 动效与声学（将静态/死板素材变活）                  │
│  ├── KEN_BURNS_MOTION   缓慢推拉摇移（图片→伪视频）    │
│  ├── AUDIO_MUTE         强制静音                      │
│  └── AUDIO_DUCKING      智能闪避混音                  │
├─────────────────────────────────────────────────────┤
│  L4: AIGC 兜底（仅当 L1-L3 完全无法覆盖时）           │
│  ├── AIGC_GENERATE      生成图片/视频/配音             │
│  └── STRUCTURE_REORDER  结构重排（降低对缺失素材依赖） │
└─────────────────────────────────────────────────────┘

> ⚠️ **[技术可行性评估]** `AIGC_GENERATE` 兜底生成：**计划采用 Doubao Seedance，但在当前一期系统中先不接入。** 当 L1~L3 策略完全无法覆盖时，将直接降级为“结构重排（STRUCTURE_REORDER）”或提示前端“需补充素材”，从而避免同步等待 AIGC 接口返回引发的 HTTP 超时。后续二期接入时需重构为强异步的 Callback / 轮询状态机模型。
```

### 策略与 FFmpeg 算子映射

| 策略类型 | FFmpeg 核心算子 | 输入 | 输出 |
|----------|----------------|------|------|
| `TRIM_AND_CUT` | `trim=start=X:end=Y, setpts=PTS-STARTPTS` | 源视频 + 时间锚点 | 裁切片段 |
| `SMART_CROP` | `crop=w:h:x:y` | 源视频 + boundingBox | 竖屏裁切 |
| `SCALE_AND_BLUR_PAD` | `split, scale, boxblur, overlay` | 横屏视频 | 竖屏+模糊背景 |
| `SPEED_RAMP` | `setpts=N*PTS, atempo=M` | 源视频 + 目标时长 | 变速片段 |
| `LOOP_SEQUENCE` | `loop / reverse + concat` | 短片段 | 循环填充 |
| `KEN_BURNS_MOTION` | `zoompan` | 静态图片 + 时长 | 伪视频 |
| `AUDIO_MUTE` | `-an` 或 `volume=0` | 带杂音视频 | 纯画面 |
| `AUDIO_DUCKING` | `sidechaincompress / amix` | 口播视频 + BGM | 混音视频 |

### 4.6.1 策略兜底与异常处理机制（已确立）

1. **`SPEED_RAMP` 边界兜底**：FFmpeg `atempo` 音频变速受限于 `[0.5x, 2.0x]`。若 LLM 给出的时长导致倍速超限，Java 侧将强制截断至该区间。对极度慢放降级为 `TRIM_AND_CUT`，对极度快进降级为 `LOOP_SEQUENCE`。
2. **`LOOP_SEQUENCE` 连贯性保障**：为避免物理 A-A-A 循环导致的跳闪感，仅针对**视觉轨道**采用 **Ping-Pong 镜像循环**（即 `A -> A倒放 -> A`，利用 FFmpeg `reverse` 滤镜），确保运动轨迹绝对连贯。
3. **`KEN_BURNS_MOTION` 公式防崩**：不在运行时动态拼接复杂的 `zoompan` 坐标，而是由 Java 侧内置 **4 种固定安全模板**（缓慢推镜头、缓慢拉镜头、缓慢左移、缓慢右移），LLM 仅可从中枚举。
4. **`AUDIO_DUCKING` 音轨补齐**：混音前置校验 `hasAudio` 属性。若用户素材无音轨，Java 侧将自动前置插入一段 `anullsrc`（静音生成器）补齐流通道，确保双轨混音滤镜正常运行。
5. **空间坐标 (Bounding Box) 拦截**：针对大模型可能产生的空间坐标幻觉，Java 端施加刚性 `Math.min(x, width)` 边界拦截。若检测到坐标离谱，强制降级为居中裁切 (Center Crop)，并在匹配结果中打上 `needsManualCorrection: true` 标记以警示人工修正。

## 4.7 LLM ↔ FFmpeg 通信协议

LLM 不直接产出 FFmpeg 命令，而是输出结构化的**策略指令（Strategy Instruction）**，由 Java 中台的 `StrategyExecutor` 翻译为具体的 FFmpeg 命令。

```
LLM 输出策略指令 JSON
        │
        ▼
Java StrategyRouter（策略路由器）
        │
        ├── 根据 strategyType 分发到对应 StrategyExecutor
        │
        ▼
StrategyExecutor（策略执行器）
        │
        ├── 将 params 翻译为 FFmpeg 命令参数
        ├── 调用 ProcessBuilder 执行 FFmpeg
        ├── 校验产物文件（检查时长/分辨率/文件大小）
        └── 返回处理结果（成功路径 or 失败原因）
```

### 策略指令标准格式

```json
{
  "strategyType": "SMART_CROP",
  "params": {
    "sourcePath": "/storage/creation/proj_xxx/raw_001.mp4",
    "outputPath": "/storage/creation/proj_xxx/adapted/seg_000_crop.mp4",
    "targetWidth": 1080,
    "targetHeight": 1920,
    "focusX": 384,
    "focusY": 378
  }
}
```

## 4.10 异步状态机与幂等性设计

### 4.10.1 异步化状态管理 (必须执行)

鉴于 `AdaptationOrchestratorService` 涉及多次耗时的 FFmpeg 调用（物理裁切、变速、混音等），**绝对不能让 Controller 直接同步等待**。
系统必须引入 **Redis 队列 + 事件驱动状态机**。
从 `ADAPTING` → `COMPOSED` 的状态跨越必须通过消息队列（或 EventBus）异步流转，防止高并发下 HTTP 线程池耗尽。

**状态流转：**
```text
DRAFT → MATCHING → MATCHED → ADAPTING → COMPOSED → EXPORTED
  │          │          │          │
  └──────────┴──────────┴──────────┴──► FAILED
```

### 4.10.2 编排协议的幂等性

核心的 `Director_Timeline_EDL` 编排协议必须保证**绝对幂等**。
无论用户在前端重排多少次，只要输入素材和模板（即 Prompt/规则）相同，就应当生成完全一致的时间轴。
- 在 `slot_match_result` 表中已引入 `version_id` 字段。
- 每次编排生成的方案都与该 `version_id` 绑定，支持随时回溯或幂等重试之前的编排结果，避免重复触发昂贵的 FFmpeg 物化计算。

## 4.11 开发者扩展点

1. **策略可插拔**：每个 `StrategyExecutor` 实现独立的 `@Component`，通过 `StrategyRouter` 按 `strategyType` 自动发现并分发
2. **AIGC 接口预留**：`AigcGenerateExecutor` 预留接口，后续可对接即梦/Runway 等生成服务

5. **批量适配**：`AdaptationOrchestratorService` 支持并行执行多个槽位的适配任务
