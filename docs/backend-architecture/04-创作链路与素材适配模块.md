# 批次 4：创作链路与素材适配模块

## 4.1 模块职责

创作链路是拆解链路的镜像对称面。拆解链路将样例视频"打碎"为结构模板；创作链路则将用户素材"填入"模板槽位，输出可编排的视频方案。

核心职责：
- 管理**创作项目（Creation Project）**，支持用户上传多类型素材（视频/图片/文本）
- 对上传素材执行**三层资产解析（Asset Profiling）**，产出标准化的资产档案
- LLM 执行**模板槽位匹配（Slot Matching）**，判断素材能否覆盖模板各段落的需求；对于完全缺失的 UI/贴纸/LOGO 类槽位，LLM 额外输出 Seedream 生图提示词
- 对不匹配的槽位，按**策略优先级梯队**自动调度 FFmpeg 处理或 Seedream 4.0 AI 生图补全
- 输出最终的**编排时间线（Composition Timeline）**，供前端可视化与成片渲染

## 4.2 创作链路全景流程

```
用户新建创作项目
        │
        ▼
上传素材（视频/图片/文本）──► 素材入库 + 异步触发资产解析
        │
        ▼
绑定/选择结构模板（从拆解链路产出的模板库中选取）
        │
        ▼
LLM 槽位匹配分析（Asset ↔ Template Segment Matching）
        │
        ├── 完全匹配 ──► 直接编排
        │
        ├── 部分匹配 ──► 进入素材适配处理链
        │   │
        │   ├── 策略梯队 L1：FFmpeg 物理变换（裁切/变速/画幅归一化）
        │   ├── 策略梯队 L2：FFmpeg 动效伪装（Ken Burns/循环拼接）
        │   ├── 策略梯队 L3：声学处理（静音/闪避混音）
        │   └── 策略梯队 L4：AIGC 生成补全（仅当 L1-L3 无法覆盖时）
        │
        └── 完全缺失 ──► LLM 评判是否可 AI 生图补位
                │
                ├── 可生图 (UI/贴纸/LOGO/插图/背景)
                │   └── Adapt 阶段异步触发 Seedream 4.0 生图
                │       ├── 成功 → IMAGE_GENERATED 资产卡片注入编排 LLM
                │       └── 失败 → 标记 FAILED，降级为结构重排
                │
                └── 不可生图 → 标记缺口 + 结构重排建议
                        │
                        ▼
                编排时间线生成（Composition Timeline）
                │
                ▼
        前端可视化展示 + 用户微调 + 成片导出
```

## 4.4 三层资产档案协议（Asset Profile Protocol）

每个上传的素材经过解析后，产出一份标准化的三层 JSON 档案。不同类型素材的协议结构在物理层和高光层有明显差异：

> [!IMPORTANT]
> `physicalAttributes` 采用“按素材类型裁剪字段”的输出策略：
> - 不适用字段不返回 `null`，而是在 JSON 中直接移除；
> - VIDEO 仅返回视频相关物理字段；IMAGE/TEXT 同理；
> - 这样可避免前端误判“空值”与“真实值缺失”。

### 4.4.1 VIDEO 素材协议示例

```jsonc
{
  "assetId": "asset_uuid",
  "assetType": "VIDEO",
  "sourcePath": "/storage/creation/proj_xxx/raw_001.mp4",

  // ═══ Layer 1: 物理属性层 ═══
  // 纯 FFmpeg/CV 计算，零幻觉
  "physicalAttributes": {
    "totalDurationSeconds": 15.0,
    "resolution": "1920x1080",
    "aspectRatio": "16:9",
    "fps": 30,
    "hasAudio": true,
    "fileSize": 12345678,
    "lighting": {
      "meanLuminance": 0.18, 
      "contrastRatio": 3.2, // (Ymax + 1.0) / (Ymin + 1.0)
      "isOverExposed": false,
      "isUnderExposed": true,
      "diagnosisStrategy": "stage_1_ffmpeg_fast"
    }
  },

  // ═══ Layer 2: 语义标签层 ═══
  // LLM 零样本感知，用于宏观匹配
  "semanticTags": {
    "mainEntities": ["马克杯", "咖啡液体", "原木桌"],
    "lightVibe": "low_key_dark",
    "overallStyle": "探店口播",
    "audioVibe": "enthusiastic_speech",     // 融合对音频情绪的感知 (若有)
    "suitableRoles": ["body", "outro"],    // LLM 推断适合的段落角色
    "emotionTone": "calm"                   // 情绪基调
  },

  // ═══ Layer 3: 高光片段层 ═══
  // 时间锚点 + 空间锚点，精准驱动裁切
  "highlights": [
    {
      "segmentId": "h_01",
      "usabilityScore": 0.1,
      "timeAnchor": { "startTime": 0.0, "endTime": 4.5 },
      "actionState": "camera_adjusting"
    },
    {
      "segmentId": "h_02",
      "usabilityScore": 0.95,
      "timeAnchor": { "startTime": 4.5, "endTime": 10.0 },
      "actionState": "pouring_coffee",
      "spokenText": "哇，这杯咖啡真的是绝了！", // 视听融合提取出的核心台词
      "cameraMovement": "static",
      "spatialAnchor": {
        "subject": "coffee_cup",
        "boundingBox": { "x": 192, "y": 216, "w": 384, "h": 324 }
      }
    }
  ]
}
```


### 4.4.4 三类素材的差异化处理流程

为了将非标准化的用户输入统一收敛为标准的三层资产档案，Java 中台针对不同 `assetType` 设计了差异化的异步解析管线（Pipeline）：

#### 1. 视频素材 (VIDEO) 处理流程
视频是信息密度最高的资产，处理管线最长，旨在提取时空双重维度的特征：
1. **物理探测 (Layer 1)**：实行**两阶段极速扫描策略**。
   - **阶段一（极速预判，耗时 < 100ms）**：运行 `ffmpeg -i input.mp4 -r 1 -vf "signalstats" -f null -`。这是一次极低 CPU 开销的扫描，直接吐出全片的亮度均值（YAVG）。如果均值在正常区间 `[0.15, 0.85]`，直接写入 Layer 1 并结束任务。
   - `contrastRatio` 由全片采样帧统计得到，计算公式固定为：`(Ymax + 1.0) / (Ymin + 1.0)`，其中 `+1.0` 用于防止极端暗帧导致除零。
   - **阶段二（模型精析，仅触发一次）**：只有当阶段一发现“均值异常”（如 `< 0.1` 或 `> 0.9`）时，才调用 Doubao 多模态模型进行“二次诊断”。让模型判断：“这是艺术化的低调摄影，还是拍摄事故（欠曝）？”
2. **场景切割 (Layer 3 预处理)**：使用算法按画面像素突变率（如 `threshold=0.4`）将长视频切分为多个物理连续的微镜头（Shots），确立坚如磐石的 `timeAnchor`。
3. **关键帧抽取与预取样缓存**：为解决前端预览性能与大模型 Token 开销，系统引入**宫格拼图法 (Grid Sequence)**。
   - 利用 FFmpeg 的 `drawtext` 在每秒抽取的关键帧上烧录鲜黄色的时序时间戳。
   - 使用 `scale & pad` 强制将任意比例单帧等比缩放并填充黑边至固定容器（如 512x512）。
   - 最后使用 `tile` 滤镜拼接为宫格大图（如 16:9 使用 2x4，9:16 使用 4x2 行列排布，确保最终图片接近 1:1）。
   - 这张极轻量的宫格图将被强缓存到 Redis 中供前端预览，**严禁在用户预览时实时调用 FFmpeg 读视频**。
4. **音频分离与 ASR (有声素材专享)**：若探测到 `hasAudio: true`，并行调用 FFmpeg 极速分离音频流，并送入 ASR 服务提取带有时间戳的字幕文本（如 SRT）。
5. **视听交叉打标 (Layer 2 & 3)**：将带有时间戳的**宫格拼图**，与**ASR 语音文稿**同时喂给 **Doubao 多模态大模型**。大模型通过交叉比对图上的视觉时间戳与 ASR 的音频时间戳，实现视听共振分析。精准输出全局风格（含 `audioVibe`）、区间 `usabilityScore`、空间锚点坐标，并将核心台词作为 `spokenText` 刻入高光片段。

#### 2. 图片素材 (IMAGE) 处理流程
图片本质上是“时间维度静止”的视频，其核心解析目标是空间识别，为后续的“动效伪装”做准备：
1. **物理探测 (Layer 1)**：读取图片宽高比、分辨率。
2. **语义感知 (Layer 2)**：调用 **Doubao 多模态大模型**识别图片中的实体物品、画风氛围，以及推测其适合在视频中扮演的段落角色（如“适合做片尾定帧”）。
3. **空间锚定 (Layer 3)**：图片没有 `timeAnchor`，但极度依赖 `spatialAnchor`。系统强制要求模型框选出核心展示主体的位置。在随后的策略梯队中，程序将结合 `KEN_BURNS_MOTION` (缓慢推拉摇移) 策略，沿着这个主体坐标将静态图片“变活”成一段 3~5 秒的动态伪视频片段。

#### 3. 文本素材 (TEXT) 处理流程
文本资产通常作为视频的包装字幕、大字报、口播旁白或提示词原材料：
1. **物理探测 (Layer 1)**：计算字数、段落结构、长短句分布。
   - `paragraphCount` 采用空行分段口径：连续空行合并为一个分隔符；全空文本计 `0`。
2. **语义提纯 (Layer 2)**：利用大语言模型对长文本进行功能分类与提纯。模型需精准识别出：哪些词句是“吸睛钩子”（适合片头），哪些是“卖点陈述”（适合主体展示），哪些是“行动号召 CTA”（适合片尾）。
3. **资产降维归宿 (Layer 3)**：文本本身不具备视觉画面，它不参与视频画面的物理裁剪。它的核心作用是在后续 LLM 槽位匹配时，作为 `text_overlay`（贴纸字幕）的填充物，或者在 L4 策略梯队中作为 AIGC 的 Prompt 输入（如生成 TTS 语音或背景图）。

### 4.4.5 素材分析 LLM 提示词分拆策略（独立模板）

为避免跨类型语义污染，素材分析不再使用融合提示词，统一改为三套独立模板：

- `CREATION_PROFILE_VIDEO_JSON`：仅用于 VIDEO。输入为“多宫格图（按页顺序）+ ASR 文本 + physicalAttributes”，输出 `semanticTags + highlights`，并强制校验 `timeAnchor`。
- `CREATION_PROFILE_IMAGE_JSON`：仅用于 IMAGE。输入为“图片 + physicalAttributes”，输出 `semanticTags + highlights`，禁止输出 `timeAnchor`。
- `CREATION_PROFILE_TEXT_JSON`：仅用于 TEXT。输入为“textContent + physicalAttributes”，输出 `semanticTags + highlights`，禁止输出 `timeAnchor/spatialAnchor`。
- VIDEO/IMAGE 的 `highlights` 中要求双轨字段并存：
  - 展示字段：`cameraMovement`、`shotType`
  - 逻辑字段：`cameraMovementTag`(`STATIC|ZOOM_IN|ZOOM_OUT|PAN|UNKNOWN`)、`shotTypeTag`(`CLOSE_UP|MID_SHOT|WIDE_SHOT|UNKNOWN`)
  - 结构评分只读取 Tag 字段，展示字段仅用于前端说明与编排解释。

调用路由固定为：`materialType -> prompt template -> payload builder -> unified parser`。  
其中：
- VIDEO/IMAGE 走 `buildMultimodalInput`（图文请求）。
- TEXT 走 `buildTextInput`（纯文本请求）。

若模型返回异常（超时/非 JSON/字段缺失），素材状态仍保持 `PROFILED`，并写入降级保底档案（`semanticTags` fallback + `highlights=[]`），日志标记 `llmDegraded=true`。

### 4.4.6 音频理解 (ASR + 音效检测) 接入建议与持久化设计

**1. 提示词与模型能力设计（与拆解流隔离）**
为了保证创作链路的纯粹性，音频分析提示词必须与原有的拆解流 (`ScriptwriterOrchestratorService` 使用的 Prompt) 物理隔离。在此链路中，我们**不仅要识别提取人声（ASR），还要具备环境音效检测（AED, Audio Event Detection）的能力**。
- **拆解流音频分析** 旨在“理解别人做好的成片”，会强调旁白结构、配乐剥离和营销意图。
- **创作流音频分析** 旨在“彻底榨取素材的声学价值”，提示词及底座模型应当侧重于以下两点：
  1. **人声台词 (Speech)**：提取纯净的原始对话、语气词（如“哇”、“我的天”）、口播情绪（激昂、低沉）。
  2. **环境/背景音效 (Sound Events)**：精准识别非人声的声学事件（如“敲击桌子声”、“水流潺潺声”、“风噪”、“急刹车声”等）。这对后续的场景氛围打标和智能闪避极具价值。
  需要强制输出带有时间戳的 JSON 格式，**绝不能夹杂任何宏观结构推演**。
- **建议新建模板**：`CREATION_AUDIO_UNDERSTANDING_PROMPT`，重点提取格式形如：`[startTime-endTime] [Type: Speech/SoundEvent] Content (Emotion/Vibe)`。

**2. 持久化位置建议**
- **方案 A（推荐）：对象存储文件**。将分析返回的完整 JSON 序列保存至素材同级目录（例如：`/storage/creation/proj_xxx/audio/raw_001_audio_analysis.json`），并在 `creative_material` 表中新增 `audio_analysis_file_path` 字段。
- **方案 B：复用现有字段**。利用 `creative_material` 表中原为 TEXT 类型预留的 `text_content` 字段，当 `material_type='VIDEO'` 且存在音频分析数据时，将 JSON 序列化存入该字段。

**3. 数据去向（在哪里需要这些数据？）**
- **下游 1：多模态视听打标（后端）**。紧接着的 `MultimodalLlmService` 需要将这份包含“台词+音效”的声学文本与宫格图一并喂给 Doubao 模型，模型借此得出全局的 `semanticTags.audioVibe` 与 `highlights.spokenText` / `highlights.backgroundSound`。
- **下游 2：智能闪避（后端策略）**。在后续 `AudioDuckingExecutor` 策略中，有了带有时间戳的声学事件（特别是人声区间），可以精确到“只有人说话的秒数区间”才压低 BGM，而非全局压低，实现影视级智能闪避。
- **下游 3：前端高级编辑器（前端）**。用户在前端微调时间线时，可以直接看到声学事件波形及台词轨道，方便手动校对、挂载贴纸以及补齐场景音效 (Foley)。

## 4.6 素材适配策略梯队（Strategy Chain）

Java 中台接收 LLM 的 `adaptationPlan`，按照策略链顺序调度 FFmpeg 或 AIGC 接口。

### 策略优先级梯队

```
┌─────────────────────────────────────────────────────┐
│  L1: 物理变换（成本最低，效果确定）                    │
│  ├── TRIM_AND_CUT      绝对时间轴裁切                │
│  ├── SMART_CROP         居中/智能裁剪                 │
│  ├── LIGHTING_ADJUST    亮度/对比度修正               │
│  └── SCALE_AND_BLUR_PAD 等比缩放+模糊填充             │
├─────────────────────────────────────────────────────┤
│  L2: 时间流控（素材时长不足/过长时）                    │
│  ├── SPEED_RAMP         变速抽插帧                    │
│  └── LOOP_SEQUENCE      无缝循环兜底                  │
├─────────────────────────────────────────────────────┤
│  L3: 动效与声学（将静态/死板素材变活）                  │
│  ├── LOCAL_BLUR         局部背景模糊（图片专用）        │
│  ├── KEN_BURNS_MOTION   缓慢推拉摇移（图片→伪视频）    │
│  └── AUDIO_MUTE         强制静音                      │
├─────────────────────────────────────────────────────┤
│  L4: AI 生图补位（仅当槽位完全 MISSING 且 LLM 判定可生图时） │
│  ├── SEEDREAM_IMAGE_GEN  调用 Seedream 4.0 异步生图       │
│  └── STRUCTURE_REORDER   结构重排（生图失败或不可生图时）   │
└──────────────────────────────────────────────────────────┘

### 4.6.1 L4: Seedream 4.0 AI 生图补位（已实现）

当 LLM 在槽位匹配阶段判定某 MISSING 槽位的缺失素材属于 **UI 装饰元素、贴纸挂件、LOGO/品牌标识、插画/示意图、纯色/渐变背景图** 等可被图片模型生成的类别时，会在 `matchDecisions` 中输出 4 个额外字段，随后在 Adapt 阶段异步触发 Seedream 4.0 生图。

**生图状态机**:

```
PENDING ──► PROCESSING ──► COMPLETED
                │
                └──► FAILED (含 errorMessage)
```

- **PENDING**: LLM 已输出生图提示词，等待 Adapt 触发
- **PROCESSING**: Adapt 阶段已将任务提交 Seedream，等待 API 返回
- **COMPLETED**: 图片 URL 已写入 `image_gen_url`，同时写入 `adapted_file_path` 供编排 LLM 消费
- **FAILED**: 生图失败，降级为结构重排

**透明背景约束**: 对于 `UI_ELEMENT` / `STICKER` / `LOGO` 类别，系统强制在 prompt 末尾追加 `transparent background, no background, isolated on transparent, PNG with alpha channel`，并注入负向提示词禁止实色背景。

**编排注入**: 生图完成后的资产以 `assetVariant=IMAGE_GENERATED` 的卡片形式进入 `buildAssetBrief()`，包含 `imageGenDescription` 中文描述和 `priorityHint` 使用建议，编排 LLM 可直接理解其语义角色。
```

### 策略与 FFmpeg 算子映射

| 策略类型 | FFmpeg 核心算子 | 输入 | 输出 |
|----------|----------------|------|------|
| `TRIM_AND_CUT` | `trim=start=X:end=Y, setpts=PTS-STARTPTS` | 源视频 + 时间锚点 | 裁切片段 |
| `SMART_CROP` | `crop=w:h:x:y` | 源视频 + boundingBox | 竖屏裁切 |
| `LIGHTING_ADJUST` | `eq=brightness=B:contrast=C` | 源视频 + 百分比调整 | 亮度/对比度修正片段 |
| `SCALE_AND_BLUR_PAD` | `split, scale, boxblur, overlay` | 横屏视频 | 竖屏+模糊背景 |
| `SPEED_RAMP` | `setpts=N*PTS, atempo=M` | 源视频 + 目标时长 | 变速片段 |
| `LOOP_SEQUENCE` | `loop / reverse + concat` | 短片段 | 循环填充 |
| `LOCAL_BLUR` | `split + boxblur/gblur + mask/overlay` | 图片 + boundingBox | 主体清晰、背景压虚 |
| `KEN_BURNS_MOTION` | `zoompan` | 静态图片 + 时长 | 伪视频 |
| `AUDIO_MUTE` | `-an` 或 `volume=0` | 带杂音视频 | 纯画面 |

> [!NOTE]
> 当前代码已落地执行器：`TRIM_AND_CUT / SMART_CROP / LIGHTING_ADJUST / LOCAL_BLUR / LOOP_SEQUENCE / KEN_BURNS_MOTION`。
> `SCALE_AND_BLUR_PAD / SPEED_RAMP / AUDIO_MUTE` 仍属于协议与文档预留项，本轮仅完成口径对齐，未补齐独立执行器。

### 4.6.1 策略兜底与异常处理机制（已确立）

1. **`SPEED_RAMP` 边界兜底**：FFmpeg `atempo` 音频变速受限于 `[0.5x, 2.0x]`。若 LLM 给出的时长导致倍速超限，Java 侧将强制截断至该区间。对极度慢放降级为 `TRIM_AND_CUT`，对极度快进降级为 `LOOP_SEQUENCE`。
2. **`LOOP_SEQUENCE` 连贯性保障**：为避免物理 A-A-A 循环导致的跳闪感，仅针对**视觉轨道**采用 **Ping-Pong 镜像循环**（即 `A -> A倒放 -> A`，利用 FFmpeg `reverse` 滤镜），确保运动轨迹绝对连贯。
3. **`KEN_BURNS_MOTION` 公式防崩**：不在运行时动态拼接复杂的 `zoompan` 坐标，而是由 Java 侧内置 **4 种固定安全模板**（缓慢推镜头、缓慢拉镜头、缓慢左移、缓慢右移），LLM 仅可从中枚举。
4. **安全滤镜隔离**：所有画面变化处理均不应破坏原视频音轨。
5. **解耦 BGM**：不再在预处理阶段处理 BGM 混音，全局配乐统一推迟至 Remotion 渲染层，防止 FFmpeg 阶段出现音频通道越界崩溃。
6. **空间坐标 (Bounding Box) 拦截**：针对大模型可能产生的空间坐标幻觉，Java 端施加刚性 `Math.min(x, width)` 边界拦截。若检测到坐标离谱，强制降级为居中裁切 (Center Crop)，并在匹配结果中打上 `needsManualCorrection: true` 标记以警示人工修正。

## 4.7 LLM ↔ FFmpeg 通信协议

LLM 不直接产出 FFmpeg 命令，而是输出结构化的**策略指令（Strategy Instruction）**，由 Java 中台的 `StrategyExecutor` 翻译为具体的 FFmpeg 命令。

```
LLM 输出策略指令 JSON
        │
        ▼
Java StrategyRouter（策略路由器）
        │
        ├── 根据 strategyType 分发到对应 StrategyExecutor
        │
        ▼
StrategyExecutor（策略执行器）
        │
        ├── 将 params 翻译为媒体处理片段（videoFilters/audioFilters/filter_complex）
        ├── 由编排器聚合为最终 FFmpeg 命令
        ├── 调用 ProcessBuilder 执行 FFmpeg
        ├── 校验产物文件（检查时长/分辨率/文件大小）
        └── 返回处理结果（成功路径 or 失败原因）
```

### 4.7.1 FFmpeg 命令串联器（当前实现）

当前编排层已从“每个策略各自输出完整命令”升级为“策略先输出片段，编排器再按媒体类型聚合命令”：

- **视频简单链**：`TRIM_AND_CUT -> SMART_CROP -> LIGHTING_ADJUST`
  - 聚合为单条视频命令，例如：`ffmpeg -ss ... -t ... -i input.mp4 -vf "crop...,scale...,eq=..." output.mp4`
- **图片预处理链**：`LOCAL_BLUR -> KEN_BURNS_MOTION`
  - 第一步输出中间图片（`.jpg/.png`）
  - 第二步再从图片生成伪视频（`.mp4`）
- **复杂音频链**：若策略产生 `audioFilters` 或显式 `filter_complex`，编排器切换到 `filter_complex` 模式并统一 `-map`

这让几何修正、调色修正、图片局部处理可以在一次转码内尽量合并，减少重复编解码损耗。

### 策略指令标准格式

```json
{
  "strategyType": "LIGHTING_ADJUST",
  "params": {
    "brightnessPercent": 12,
    "contrastPercent": 18,
    "reason": "画面偏灰且主体曝光不足，需要轻度提亮并增强层次"
  }
}
```

图片局部模糊策略示例：

```json
{
  "strategyType": "LOCAL_BLUR",
  "params": {
    "boundingBox": { "x": 100, "y": 200, "w": 880, "h": 600 },
    "blurStrength": 18,
    "featherPercent": 8,
    "reason": "背景信息较杂，先压虚背景再做轻推镜，主体更突出"
  }
}
```

## 4.10 异步状态机与幂等性设计

### 4.10.1 异步化状态管理 (必须执行)

鉴于 `AdaptationOrchestratorService` 涉及多次耗时的 FFmpeg 调用（物理裁切、变速等），**绝对不能让 Controller 直接同步等待**。
系统必须引入 **Redis 队列 + 事件驱动状态机**。
从 `ADAPTING` → `COMPOSED` 的状态跨越必须通过消息队列（或 EventBus）异步流转，防止高并发下 HTTP 线程池耗尽。

**状态流转：**
```text
DRAFT → MATCHING → MATCHED → ADAPTING → COMPOSED → EXPORTED
  │          │          │          │
  └──────────┴──────────┴──────────┴──► FAILED
```

### 4.10.2 编排协议的幂等性

核心的 `Director_Timeline_EDL` 编排协议必须保证**绝对幂等**。
无论用户在前端重排多少次，只要输入素材和模板（即 Prompt/规则）相同，就应当生成完全一致的时间轴。
- 在 `slot_match_result` 表中已引入 `version_id` 字段。
- 每次编排生成的方案都与该 `version_id` 绑定，支持随时回溯或幂等重试之前的编排结果，避免重复触发昂贵的 FFmpeg 物化计算。

```text
    -> 查询项目下 PROFILED 素材
    -> 聚合素材 semanticTags 为 queryText
    -> 向量召回候选模板（topK = topN * 2）
    -> 对每个候选读取 templateJson（按 templateId + templateVersion）
    -> 结构评分（Canonical 归一化后打分）
    -> 结构 veto 过滤（score < 0 的候选直接淘汰）
    -> finalScore = semanticScore * w1 + structureScore * w2
    -> 按 finalScore 降序排序 + 截断 topN + rank 编号
  -> 返回推荐结果
```

### 4.13.2 阶段明细与数据来源

| 阶段 | 处理逻辑 | 关键输入字段 | 关键输出 |
|------|----------|--------------|----------|
| 1. 素材过滤 | 仅取 `status=PROFILED` 的素材 | `creative_material.status` | 待评分素材池 |
| 2. 语义检索 Query 构造 | 逐素材读取 `profileJson.semanticTags`，拼接为文本 | `profileJson.semanticTags` | `queryText` |
| 3. 向量召回 | 在 `creation_template` 集合做 `similaritySearch(topK)` | `queryText` | 候选模板列表 |
| 4. 候选结构加载 | 按 `templateId + templateVersion` 回查模板 JSON | `deconstruct_template.template_json` | `templateJson` |
| 5. 字段归一化 | 模板/素材统一映射到 Canonical Tag | `segments[]` 新抽象字段 + `shots[]` fallback、`highlights[]` | `cameraMovementTag`、`shotTypeTag`、`requiredVisualFunctions` |
| 6. 结构评分 | 按段逐一选最佳素材并累计分值 | Canonical 字段 + 基础物理字段 | `structureScore` |
| 7. 分数融合 | 语义分与结构分加权融合 | `semanticScore`、`structureScore` | `finalScore` |
| 8. 排序返回 | 降序、截断、排名 | `finalScore` | 推荐列表 |

### 4.13.3 Canonical 字段契约（结构分只读）

为避免“自然语言字段不生效”，结构评分当前优先读取以下刚性字段：

- 段落级视觉偏好：
  - `scriptStructure.segments[].preferredCameraMovements`
  - `scriptStructure.segments[].preferredShotTypes`
  - `scriptStructure.segments[].requiredVisualFunctions`

- 运镜标签 `cameraMovementTag`：`STATIC | ZOOM_IN | ZOOM_OUT | PAN`
- 镜头标签 `shotTypeTag`：`CLOSE_UP | MID_SHOT | WIDE_SHOT`

兼容策略：

1. **模板侧**优先读取 `segments[]` 中的新抽象字段。
2. 若模板侧缺失新字段，则回退读取 `shots[]` 中的 `shotTypeTag / cameraMovementTag`。
3. **素材侧**优先读取 `highlights[]` 中的 `*Tag` 字段。
4. 若缺失，则从自然语言字段（`cameraMovement`、`shotType`）做关键词映射。
5. 映射失败标记为 `UNKNOWN`，并进入惩罚分逻辑。

说明：

- `requiredVisualFunctions` 已进入结构评分与缺口识别主链；
- 自然语言字段仍保留用于展示与解释，不作为结构分主判据。

### 4.13.4 结构分计算规则（当前实现口径）

设模板有 `N` 个 segment，先做逐段匹配，再对段分求均值：

1. 对每个 segment，在全部候选素材中计算段分，取最高值作为该段最佳素材分。
2. 若该段触发硬 veto（见下）则模板整体淘汰（结构分返回 `-1`）。
3. 最终结构分：

```text
structureScore = (segmentBestScore_1 + ... + segmentBestScore_N) / N
```

段内扣分项（初始分 1.0）：

- `cameraMovementTag` 未知或素材侧未知：`-0.1`
- `shotTypeTag` 不匹配：`-0.2`
- `shotTypeTag` 未知：`-0.1`
- `requiredVisualFunctions` 未被素材支撑：按缺失数量累积扣分（当前实现为“功能匹配加分/扣分”）
- `suitableRoles` 不包含当前 `segment.role`：`-0.3`
- 素材时长小于 `segment.durationRange.min`：按差值扣分 `diff * 0.05`
- 画幅比例偏差过大（>0.1）：`-0.05`
- `lightVibe` 命中暗光/过曝风险词：`-0.05`
- 模板 `acousticEnvironment=asmr` 且素材声场噪杂：`-0.4`

硬 veto 条件（当前最关键）：

- 模板段需要动态运镜（非 `STATIC`）；
- 素材为 `VIDEO` 且可判定素材运镜已知；
- 但素材全部高光都表现为静态；
- 则该段判定不可用，模板直接 veto。

### 4.13.5 最终融合公式与排序

语义分来自向量召回候选（基于向量距离换算），结构分来自规则评分：

```text
finalScore = semanticScore * w1 + structureScore * w2
```

其中：

- `semanticScore`：候选模板与素材语义相似度
- `structureScore`：模板结构可落地性
- `w1/w2`：权重参数（由请求传入）

排序策略：

1. 先过滤 `structureScore < 0`（veto）
2. 按 `finalScore` 降序
3. 取 `topN`
4. 生成 `rank`（从 1 开始）

### 4.13.6 可观测性与生效率监控

结构评分链路输出以下核心日志指标：

- `templateMissingTagCount`
- `materialMissingTagCount`
- `fallbackMappingCount`
- `unknownTagPenaltyCount`
- `fieldCoverage`
- `vetoReason`

告警阈值：

- `fieldCoverage < 0.85` 触发低覆盖率警告，提示 Tag 契约落实不足。

### 4.13.7 兜底与边界行为

- 无 `PROFILED` 素材：返回空推荐列表。
- 模板 JSON 缺失或解析异常：该候选跳过。
- 结构评分异常：该候选结构分按 `0.0` 处理（非 veto），保留链路稳定性。

## 4.14 智能 BGM 推荐子系统设计

### 4.14.1 设计背景与动机

传统的模板绑定方案将背景音乐（BGM）固死在模板内部。然而，即使套用相同模板，用户上传的实际视频素材也具有不同的情绪基调与节奏张力。为了让视频成片的声画契合度达到最优，系统设计了以**实际素材语义特征**为核心、**绑定模板声学结构**为物理约束的**多模态智能 BGM 推荐子系统**。

### 4.14.2 核心流程与数据同步

```
 用户上传素材（已解析 Profile）+ 已确定绑定模板
                        │
                        ▼
 聚合素材画像文本（风格、情绪、实体标签、模板基本描述）
                        │
                        ▼
1. 向量库粗筛阶段：向 Chroma db 检索 [creation_bgm] 独立集合，召回 TopK 候选
                        │
                        ▼
2. 物理校验与精排阶段：
   ├── Hard Veto (一票否决) ──► 模板 acousticEnvironment == asmr 且音频为重节奏风格 ──► 剔除
   ├── w1：语义匹配度评分 (Semantic Similarity)
   ├── w2：段落能量起伏对齐评分 (Energy Curve Alignment)
   └── w3：时长与 BPM 物理特征适配评分 (Duration Penalty & BPM Match)
                        │
                        ▼
                  综合得分排序：
   finalScore = (w1 * semanticScore) + (w2 * energyCurveScore) + (w3 * durationBpmScore)
                        │
                        ▼
   前端调试测试床（BgmMatchDebug）/ 创作工作流渲染展现 (TopN)
```

#### Chroma 独立集合隔离
为防检索污染，Chroma 数据库中创建了独立的 `creation_bgm` 集合，仅存储和同步系统 BGM 档案，不与 `creation_template` 等混用。
在 `BgmVectorInitRunner` 中实现冷启动同步逻辑：
- 扫描 `/storage/audio-database` 目录下的所有音频，提取其元数据 `audio_data.json`（BPM、时长、主风格标签等）。
- 将音频整体风格及节奏描述转化为特征自然段，生成向量存入 `creation_bgm`；同时在 metadata 中绑定 `bpm`、`durationSeconds`、`filePath` 等用于精排计算的硬字段。

### 4.14.3 三维精排算法实现

#### 1. 语义匹配评分 ( S<sub>semantic</sub> )
- **输入**: 素材语义标签（`overallStyle`、`emotionTone`、`mainEntities`）与所绑定模板的描述，通过分词和拼接组成查询句。
- **计算**: 从 Chroma 向量库中检索得到余弦相似度 *D* ，将其归一化作为语义分：

$$
S_{\text{semantic}} = \max(0.0, 1.0 - D)
$$

#### 2. 能量曲线匹配评分 ( S<sub>energy</sub> )
- **背景**: 视频模板的每个镜头有其预期的视觉动能起伏（例如：Hook 弱，Climax 极强，Outro 弱），BGM 应该在对应的绝对时间区间呈现相吻合的声音能量（dB / 振幅 RMS）。
- **计算**: 对齐模板各 Segment 的时间轴，提取对应时间段 BGM 的实际能量，计算期望与实际的均方误差（MSE）：

$$
S_{\text{energy}} = \frac{1}{1.0 + \text{MSE}(\mathbf{E}_{\text{template}}, \mathbf{E}_{\text{audio}})}
$$

#### 3. 时长物理适配评分 ( S<sub>duration_bpm</sub> )
- **背景**: BGM 的物理时长需尽量覆盖视频总时长。若音频时长短于视频模板，则需进行循环播放，但这会带来割裂感，必须引入惩罚机制。
- **计算**: 
  - 若 L<sub>audio</sub> ≥ L<sub>template</sub> ，扣分为 0；
  - 若 L<sub>audio</sub> < L<sub>template</sub> ，计算循环次数 N = ⌈ L<sub>template</sub> / L<sub>audio</sub> ⌉ ，对其施加指数衰减扣分：

$$
S_{\text{duration\_bpm}} = S_{\text{base\_bpm\_match}} \times (0.9)^{N-1}
$$

### 4.14.4 强匹配一票否决规则（ASMR Hard Veto）

若模板对环境声有刚性低噪诉求（例如 `acousticEnvironment = asmr` ），任何被解析为重低音、摇滚、电子、Hip-hop 等风格的 BGM（包括但不限于 `hip_hop_beat`, `travel_trance`, `electronic`, `rock`）将触发一票否决，直接从最终推荐结果中过滤（或打分设为 `-1.0`），确保声画氛围一致。

### 4.14.5 前端调试工作台设计

为了让运营人员能够直观测出最优的 w<sub>1</sub>, w<sub>2</sub>, w<sub>3</sub> 比例，前端在 `/create/detail/:projectId/bgm-debug` 页面提供了一个**三维权重调优工作台**。

#### 1. 权重自平衡联动算法
因为 w<sub>1</sub> + w<sub>2</sub> + w<sub>3</sub> = 1.0 的刚性约束，用户拖动其中任一滑块时，其余两个滑块需等比例自适应伸缩，其数学联动方程为：
设本次被拖动的权重为 w<sub>i</sub> ，改变后的值为 w'<sub>i</sub> ，其余两个权重为 w<sub>j</sub>, w<sub>k</sub> ，则它们的更新值为：

$$
w'_j = \frac{w_j}{w_j + w_k} \times (1.0 - w'_i)
$$

$$
w'_k = \frac{w_k}{w_j + w_k} \times (1.0 - w'_i)
$$

#### 2. 自包含 CSS 健壮设计
为了防止在复杂的非 Tailwind 线上编译环境下因样式丢失导致页面塌陷（如 SVG 巨大化等），`BgmMatchDebug.tsx` 页面采用**局部 scoped CSS 标签内嵌设计**。通过将全套暗黑质感、流光渐变按钮、磨砂玻璃面板及 HTML5 原生播放状态图标封装在组件自包含的 `<style>` 标签中，确保了在任何微前端/独立部署形态下的视觉呈现一致性和可维护性。
