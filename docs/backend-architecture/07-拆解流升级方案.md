# 批次 7：拆解流升级方案

## 7.1 背景与目标

当前视频拆解主链已经具备完整闭环：

- `LocalFfmpegSceneDetectorEngine` 负责镜头切分，产出 `SceneShot`
- `KeyFrameAnalysisService` 负责关键帧抽取
- `TimelineMatcherService` 将 `scene_result.json + ASR + key_frame` 归一为胖时间线
- `StructureAnalyzerServiceImpl` 基于 `timelineMarkdown + 离散关键帧图片` 做结构模板分析

这条链已经足以支撑：

- 视频基础拆解
- 模板初版生成
- 下游创作链路的模板绑定与素材匹配

但随着创作链路进入“素材缺口识别 + 素材补全 + Remotion 编排”阶段，上游拆解精度开始成为明显瓶颈。当前关键问题不是“链路能不能跑通”，而是：

- 离散关键帧过稀，难以稳定支撑镜头职责判断
- 对剪辑手法、节奏变化、包装密度的视觉证据不足
- 模板拆解精度限制了下游缺口识别与补全质量

因此，本轮升级目标不是一步到位重写整条拆解链，而是走**低风险、高收益的分阶段升级路线**：

- **P0**：保留当前离散关键帧主链，升级为“Hook-Locking + 镜头边界补帧 + 少量均匀采样”
- **P1**：在此基础上，为重点段落引入**局部宫格增强**，让 LLM 更稳定判断剪辑手法、段落结构、节奏结构与包装结构

这份文档是独立升级方案，不直接替换现有 [02-视频拆解分析模块.md](./02-%E8%A7%86%E9%A2%91%E6%8B%86%E8%A7%A3%E5%88%86%E6%9E%90%E6%A8%A1%E5%9D%97.md) 的总览描述。原因是当前生产链路仍在运行，旧文档承担“现状说明”，本文件承担“升级设计与实施计划”。

## 7.2 当前拆解流现状

### 7.2.1 上游代码链现状

当前拆解流的核心代码链如下：

1. `LocalFfmpegSceneDetectorEngine`
   - 使用 FFmpeg `scdet` 能力，输出 `SceneShot`
   - 每个 `SceneShot` 已包含：
     - `startTime`
     - `endTime`
     - `duration`
     - `sceneScore`

2. `KeyFrameAnalysisService`
   - 当前使用典型的 **Hook-Locking 稀疏抽帧** 策略
   - 首镜头固定抽：
     - `HOOK_FIRST`
     - `HOOK_MID`
   - 其余镜头按 `sceneScore` 排序补帧
   - 当前 `maxFrames` 动态上限约为 `5 ~ 15`

3. `TimelineMatcherService`
   - 将 `scene_result.json + ASR + key_frame` 归一为胖时间线
   - 在微碎段提纯时，使用 `containsKeyFrame(...)` 判断一个 segment 是否“值得保留”
   - 会为 segment 推断 `phaseHint`，当前可见：
     - `HOOK_CANDIDATE`
     - `BODY`
     - `BODY_CLIMAX`
     - `CTA_CANDIDATE`

4. `StructureAnalyzerServiceImpl`
   - 当前输入形态不是宫格图主导，而是：
     - `TimelinePromptFormatter` 生成的 `timelineMarkdown`
     - 若干离散关键帧图片
   - 图片通过 `IMAGE_XXX` 标签与时间线对齐
   - 最终由 `STRUCTURE_ANALYZER_UNIFIED` Prompt 引导 LLM 进行三类结构抽取

### 7.2.2 当前链路的优点

当前实现已经具备这些优点：

- 有真实的 cut 点结果，不需要从零补场景检测能力
- 抽帧接口本身就是“按时间戳抽图”，非常适合扩时间点策略
- 上游结构分析已具备多模态图文输入能力，不必重新铺 LLM 主链
- 下游创作素材分析已经有成熟宫格能力，可以在 P1 复用

### 7.2.3 当前链路的主要瓶颈

当前最主要的问题不是“切分不到镜头”，而是“视觉证据密度不够”：

1. 关键帧过稀
   - 当前更偏“代表帧抽样”
   - 对镜头切换前后发生了什么，证据不足

2. 镜头职责难以稳定判断
   - 单帧更适合做内容摘要
   - 但不适合稳定判断：
     - 开头 Hook
     - 使用过程镜头
     - 节奏高潮段
     - 结尾 CTA 段

3. 剪辑手法与包装结构证据不足
   - 节奏结构需要看到画面变化密度
   - 包装结构需要看到字幕/标题条/贴纸/转场在一段时间内如何出现与消失
   - 离散关键帧无法充分表达这些连续变化

4. 下游问题会被上游放大
   - 模板拆解若没识别出“过程镜头”或“高潮快切”，下游就很难准确判断素材缺口
   - 后续补全策略即使变多，也会建立在不稳定的模板理解上

## 7.3 升级目标

本轮拆解流升级的目标分为三层：

### 7.3.1 结构目标

- 提升镜头级理解能力
- 提升脚本/段落结构抽取可信度
- 提升节奏结构抽取可信度
- 提升包装结构抽取可信度

### 7.3.2 工程目标

- 尽量不打断现有拆解主链
- 优先复用已有 `SceneShot`、按时间戳抽帧、下游宫格生成等现有能力
- 将改动控制在：
  - 抽帧策略
  - Prompt 解释力
  - 冷数据扩展

### 7.3.3 演进目标

- 与下游素材分析的“宫格时序理解范式”逐步靠拢
- 但不强行一步到位改为“全片 16 帧宫格 1s 采样主链”

---

## 7.4 总体升级策略

### 7.4.1 为什么不建议一步到位全量宫格化

从方向上看，宫格更利于 LLM 理解：

- 剪辑手法
- 段落结构
- 节奏变化
- 包装密度

但从当前代码链来看，一步到位把上游全面改成“全片宫格主输入”代价过大，因为它会同步牵动：

- 关键帧生成策略
- 图片发送组织方式
- `TimelinePromptFormatter` 的标签体系
- Prompt 的阅读逻辑
- 时间线与图片的对齐方式

因此，当前更适合的路线是：

1. **P0：先扩时间点策略**
2. **P1：再对重点段落引入局部宫格**

这是一个“先稳住收益，再逐步提升结构理解精度”的演进路径。

### 7.4.2 推荐路线

- **P0**：边界补帧增强
  - 保留离散关键帧主链
  - 优先解决“切换点证据不足”的问题

- **P1**：局部宫格增强
  - 不改全片主协议
  - 只给重点段落追加高密视觉证据

## 7.5 P0 升级方案：边界补帧增强

### 7.5.1 核心思想

P0 的核心思想是：

> 先不改上游主协议，只改关键帧时间点生成策略。

即：

- 保留当前离散关键帧主链
- 保留 `StructureAnalyzerServiceImpl` 当前“时间线 + 离散关键帧图片”的输入范式
- 仅增强“关键帧选点”，让模型看到更多切换前后的证据

### 7.5.2 抽帧策略升级

当前 `KeyFrameAnalysisService.selectKeyFrameInfos(...)` 的策略是：

- 首镜头 2 帧：
  - `HOOK_FIRST`
  - `HOOK_MID`
- 其余镜头按 `sceneScore` 排序取中点

P0 推荐升级为：

1. 保留首镜头：
   - `HOOK_FIRST`
   - `HOOK_MID`

2. 对高价值 cut 点补帧：
   - `cut - delta`
   - `cut + delta`

3. 对长镜头保留中点帧：
   - 避免长镜头只有边界、没有中间证据

4. 对全片增加低密度均匀采样兜底：
   - 推荐 `每 2s 1 帧`
   - 不是 `每 1s 全量铺开`

5. 去重规则继续保留
   - 避免过密时间点落到同一帧附近

### 7.5.3 推荐默认参数

P0 建议默认参数如下：

- `boundaryDeltaSec`: `0.15`
- `uniformSampleIntervalSec`: `2.0`
- `longShotMidpointThresholdSec`: `2.5`
- `maxFrames`: 从当前 `<=15` 提升到建议 `<=24`
- `cutScoreThresholdForBoundaryBoost`: 复用或轻微高于当前 timeline 默认高敏阈值

### 7.5.4 为什么当前代码更适合这个方案

当前代码非常适合先做 P0，原因如下：

1. `KeyFrameExtractEngine` 本来就是“给时间戳列表 -> 抽图”
2. `SceneShot` 已经有切分边界，无需新增场景检测能力
3. `StructureAnalyzerServiceImpl` 可继续吃离散关键帧，不破坏上游主链
4. 对 `TimelinePromptFormatter` 的改动可控制在补充更多 frame role / 时间锚，不需要重构输入协议

### 7.5.5 P0 建议修改模块

P0 的建议改造模块如下：

1. `KeyFrameAnalysisService`
   - 核心改造点
   - 负责生成更多、更合理的时间点

2. `TimelinePromptFormatter`
   - 在 Markdown 中更清楚地区分不同关键帧角色
   - 让 LLM 明确哪些是 Hook 帧、边界补帧、均匀采样帧

3. `ArkPromptTemplates.STRUCTURE_ANALYZER_UNIFIED`
   - 增强对“连续帧变化”的解释指引
   - 明确要求模型利用帧间变化判断结构角色与节奏变化

## 7.6 P1 升级方案：局部宫格增强

### 7.6.1 核心思想

P1 的核心思想是：

> 不把全片主输入立刻切成宫格，而是只给“重点段落”补局部高密视觉证据。

这一步的目标不是推翻 P0，而是在 P0 基础上补一个更强的“局部连续证据层”。

### 7.6.2 为什么宫格对结构分析更有价值

宫格的核心价值不是“多看几张图”，而是更利于 LLM 理解：

- 镜头关系
- 变化密度
- 视觉节奏
- 包装模式

具体来说，宫格更适合 LLM 判断：

1. 脚本/段落结构
   - 开头 Hook 是否快速建立主题
   - 中段是否在连续展开卖点
   - 结尾是否在做 CTA 收束

2. 节奏结构
   - 镜头切换频率
   - 快慢变化
   - 高潮位置

3. 包装结构
   - 字幕密度
   - 标题条是否高频出现
   - 贴纸与转场是否集中在某段

### 7.6.3 重点段落来源

P1 建议只为重点段落生成局部宫格。重点段落可来自：

- `TimelineMatcherService` 中切分速率高、`avgSceneScore` 高的段
- `inferPhaseHint(...)` 推定的：
  - `HOOK_CANDIDATE`
  - `BODY_CLIMAX`
  - `CTA_CANDIDATE`
- 关键帧不足但时长较长的段
- 包装元素疑似高频出现的段

### 7.6.4 实现方式

P1 复用下游已有的宫格生成能力：

- `LocalCreationFfmpegEngine.generateGridSequencePages(...)`

但不复用“整素材全分页宫格”的策略，而是改成：

- 对指定 segment 生成**局部宫格页**

推荐默认：

- `8` 或 `12` 帧一页
- 每格带时间戳
- 采样以“段内均匀 + cut 附近补采样”为主

### 7.6.5 P1 多模态输入升级

当前 `StructureAnalyzerServiceImpl` 的主输入是：

- `timelineMarkdown + discrete keyframes`

P1 升级为：

- `timelineMarkdown + discrete keyframes + optional segment grids`

也就是说：

- 保留原有离散关键帧作为“全局锚点”
- 用 segment grid 补重点段的“连续视觉证据”

### 7.6.6 为什么不建议一上来就全量 16 帧宫格

虽然“全片 16 帧宫格 + 每 1s 采样一次”听起来统一，但当前并不适合作为第一步：

1. 当前 `StructureAnalyzerServiceImpl` 的图片组织方式是单图按顺序注入
2. `TimelinePromptFormatter` 当前用 `IMAGE_XXX` 与离散关键帧对齐
3. 一次性切成“全片宫格主输入”会同步牵动：
   - prompt 设计
   - 图片标签体系
   - 时间线对齐方式
   - 模型阅读策略

因此，**局部宫格增强**是更现实的中间态：

- 风险更低
- 更容易验证收益
- 更适合与当前代码链兼容

## 7.7 协议变更方案

### 7.7.1 P0：最小协议变更

P0 不新增数据库表，优先复用现有结构，仅补字段语义。

#### 1. `key_frame.extraction_reason`

当前已有：

- `HOOK_FIRST`
- `HOOK_MID`
- `TOP_SCORE`

P0 推荐新增：

- `BOUNDARY_PRE`
- `BOUNDARY_POST`
- `UNIFORM_SAMPLE`
- `LONG_SHOT_MID`

说明：

- 该字段本身已经存在，不需要改表结构
- 只需扩展枚举语义

#### 2. `TimelinePromptFormatter`

建议升级输出口径：

- 对关键帧增加更明确的 frame role 解释
- 在 Markdown 中区分：
  - Hook 锁定帧
  - 边界补帧
  - 均匀采样帧
  - 长镜头中点帧

目标是让 LLM 不只“看到一张图”，还知道“为什么系统选了这张图”。

#### 3. `STRUCTURE_ANALYZER_UNIFIED` Prompt

建议增加这些说明：

- 如何利用边界补帧判断剪辑手法与结构角色
- 如何利用连续帧变化判断：
  - `hook`
  - `body`
  - `climax`
  - `outro`
- 如何利用帧间变化判断：
  - 节奏变化
  - 包装密度变化

### 7.7.2 P1：局部宫格协议升级

P1 需要新增“局部宫格资产”的表达，但**不建议一开始就改主表设计太深**。

建议有两种方案：

#### 方案 A：在冷数据 JSON 中补 `segmentGridAssets`

优先推荐。

在：

- `fatTimelineJson`
- `refinedTimelineJson`

中附加：

- `segmentGridAssets[]`

每项建议包含：

- `segmentId`
- `pageIndex`
- `filePath`
- `frameCount`
- `gridCols`
- `gridRows`
- `samplingStrategy`

优点：

- 对数据库侵入小
- 对现有表结构影响小
- 兼容旧任务更容易

#### 方案 B：新增 `timeline_segment_grid` 表

更规范，但改动更大。

优点：

- 数据模型更标准
- 更适合未来前端与批量审查读取

缺点：

- 需要单独 migration
- 需要补 Mapper / Entity / 读写流程

本轮推荐先采用 **方案 A**。

#### Prompt 侧配套升级

Prompt 文本中需要显式说明：

- 宫格图代表某个 segment 的高密视觉证据
- 每格带时间戳
- 画面顺序按：
  - 从左到右
  - 从上到下
  - 时间递增

## 7.8 更改风险点与回滚策略

### 7.8.1 业务风险

1. 帧数增多后，LLM 输入成本上升
2. 上游模板拆解结果可能与现有模板产出风格产生偏差
3. 模板推荐链、下游匹配链在短期内会出现“新旧模板理解口径并存”

### 7.8.2 技术风险

1. `KeyFrameAnalysisService` 抽帧数量提升后，磁盘 IO 和图片读取成本上升
2. `StructureAnalyzerServiceImpl` 多图输入变多后，请求体增大，可能增加方舟响应时延与失败率
3. 若直接全量宫格化，`TimelinePromptFormatter` 与 `IMAGE_XXX` 对齐体系会变复杂
4. 若宫格页过大或过密，反而导致 LLM 看不清细节

### 7.8.3 兼容风险

1. `TimelineMatcherService.containsKeyFrame(...)` 当前用“是否有关键帧”来决定碎段提纯；若补帧数量显著增加，可能导致更多微段被保留，需要重新校准 `timeline.min-segment-duration-sec`
2. 现有文档里写过“≤5 张关键帧”的口径，需要同步修订，避免设计文档与代码不一致
3. 若未来引入局部宫格，前端若读取冷数据展示，也要注意兼容旧任务无宫格字段的情况

### 7.8.4 回滚策略

#### P0 回滚

P0 具备天然的低风险回滚条件：

- 抽帧接口不变
- 数据表不变
- 只需回退 `selectKeyFrameInfos(...)` 时间点策略即可

#### P1 回滚

P1 若采用冷数据 JSON 扩展方式：

- 移除 `segmentGridAssets`
- Prompt 不再消费 grid 图
- 离散关键帧主链仍可单独工作

因此 P1 也具备较好的灰度与回滚条件。

## 7.9 升级步骤建议

### 7.9.1 P0 实施步骤

建议按以下顺序落地：

1. 升级 `KeyFrameAnalysisService`
   - 引入边界补帧
   - 引入长镜头中点帧
   - 引入低密度均匀采样
   - 保留去重与总上限控制

2. 升级 `TimelinePromptFormatter`
   - 在 Markdown 中明确 frame role
   - 保持与 `IMAGE_XXX` 标签体系兼容

3. 升级 `STRUCTURE_ANALYZER_UNIFIED`
   - 告诉 LLM 如何利用补帧判断结构角色、节奏与包装变化

4. 校准 `TimelineMatcherService`
   - 重点观察 `containsKeyFrame(...)`
   - 评估 `timeline.min-segment-duration-sec` 是否需要调校

5. 做灰度验证
   - 先跑快切节奏型、产品展示型、口播教程型三类样例

### 7.9.2 P1 实施步骤

建议按以下顺序落地：

1. 复用 `LocalCreationFfmpegEngine.generateGridSequencePages(...)`
   - 对指定 segment 生成局部宫格页

2. 扩展冷数据 JSON
   - 在 `fatTimelineJson / refinedTimelineJson` 中增加 `segmentGridAssets[]`

3. 升级 `StructureAnalyzerServiceImpl`
   - 在原有离散关键帧输入之上，追加可选的 segment grid 输入

4. 升级 `STRUCTURE_ANALYZER_UNIFIED`
   - 明确说明如何阅读宫格时序图

5. 做对照实验
   - 对比 P0 与 P1 在脚本结构、节奏结构、包装结构上的稳定性差异

## 7.10 测试计划

### 7.10.1 P0

#### 1. 关键帧策略

- 同一个视频任务，验证抽帧数量从旧策略提升，但不超过新上限
- 检查 `key_frame.extraction_reason` 是否覆盖：
  - Hook
  - 边界补帧
  - 均匀采样
  - 长镜头中点
- 验证 cut 点前后确实存在补帧

#### 2. Timeline 影响

- `TimelineMatcherService` 在更高帧密度下仍能稳定生成 `fatTimeline`
- 微碎段提纯结果不出现异常膨胀
- `phaseHint` 输出分布更合理，尤其：
  - `HOOK_CANDIDATE`
  - `BODY_CLIMAX`
  - `CTA_CANDIDATE`

#### 3. LLM 结构分析

同一素材对比旧策略与新策略，重点检查：

- `scriptStructure.segments`
- `rhythmStructure.overallPace`
- `climaxPositions`
- `packagingStructure`

至少选 3 类视频验证：

- 快切节奏型
- 产品展示型
- 口播教程型

### 7.10.2 P1

#### 1. 局部宫格生成

- 指定 segment 能生成 8/12 帧宫格图
- 宫格带时间戳，顺序正确
- `segmentGridAssets` 正确落到冷数据 JSON

#### 2. LLM 输入效果

  - 快切
  - 镜头推进
  - 字幕密度变化
  - 包装高频段

#### 3. 回归

- 旧任务无宫格字段时，拆解结果仍可读取
- 非重点段无宫格时，主链不报错
- 模板发布、推荐、绑定、创作链路不受协议兼容影响

## 7.11 最终建议

基于当前代码链，最可行的升级方向不是“一步到位把上游完全切成和下游一致的 16 帧宫格 1s 采样主链”，而是：

1. **P0：边界补帧增强**
   - 先把稀疏关键帧升级成更能表达镜头变化的离散证据链

2. **P1：局部宫格增强**
   - 再为重点段落补连续高密视觉证据

这是当前最平衡的方案：

- 和现有代码链兼容性最好
- 风险最低
- 收益最直接
- 也最符合“先增强结构理解，再反哺下游缺口识别与补全”的业务路径

如果后续验证证明“局部宫格显著优于离散关键帧”，再考虑更大范围地推进上游宫格主导输入，才是更稳妥的工程节奏。
