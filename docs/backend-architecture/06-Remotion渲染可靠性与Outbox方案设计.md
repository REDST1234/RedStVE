# 批次 6：Remotion 渲染可靠性与 Outbox 方案设计

## 6.1 背景与目标

当前项目已经完成了 Remotion 渲染微服务的基础拆分，链路已经具备“可以跑通”的能力：

- Java 侧负责创作项目、素材组织、脚本编排与渲染任务发起
- RabbitMQ 负责把渲染任务异步投递给 Remotion
- Remotion 负责真正的渲染执行
- Java 再通过轮询状态或补偿逻辑感知渲染结果

从微服务学习阶段来看，这意味着我们已经跨过了“单体内直接调用”的阶段，进入了更有代表性的主题：

- 服务间异步通信
- 最终一致性
- 消息投递可靠性
- 执行现场状态与业务真相状态分离
- 故障、超时、人工重试的制度化设计

本文档的目标不是一次性补齐所有生产级能力，而是基于当前仓库事实，沉淀一版**可落地、边界清晰、可继续演进**的渲染可靠性方案。重点回答：

1. 为什么当前链路已经不适合继续停留在“业务代码直接发 MQ”
2. 为什么要引入 `Outbox + 幂等 + 状态机`
3. 第一版到底定了哪些策略，哪些点明确延期到二期
4. 如何把我们多轮头脑风暴的取舍结果沉淀成工程文档，而不是停留在讨论

## 6.2 当前链路与真实风险

### 6.2.1 当前渲染链路

当前主链路可以概括为：

```text
用户点击“渲染”
   ->
Java 生成 renderId、编排 CompositionScript
   ->
CreationProjectServiceImpl 直接调用 RemotionServiceClient.submitRenderTask()
   ->
RabbitTemplate.convertAndSend(...) 发往 RabbitMQ
   ->
Remotion 消费队列并执行渲染
   ->
Remotion 将任务状态保存在内存 + Redis
   ->
Java 通过轮询 / 同步逻辑更新 render_record
```

结合当前代码，几个关键事实很明确：

- `CreationProjectServiceImpl.generateVideoInternal()` 中，业务代码会在生成脚本后立即调用 `remotionServiceClient.submitRenderTask(renderId, script)`。
- `RemotionServiceClient.submitRenderTask()` 当前直接通过 `rabbitTemplate.convertAndSend(...)` 发消息。
- `render_record` 当前只承担 `QUEUED / RENDERING / DONE / FAILED` 这类业务状态。
- Remotion 侧虽然会把状态写入 Redis，但执行现场主状态仍然是进程内 `Map`。
- Java 侧已经存在死信补偿和同步退款逻辑，说明系统已经开始感知“消息发不出去”和“消息消费失败”是两类不同故障。

### 6.2.2 当前问题不是不能跑，而是不够可靠

当前实现的价值在于它证明了“微服务链路可跑通”，但如果继续沿用，会遇到几个典型可靠性缺口。

#### 1. 业务事务与消息投递存在双写不一致窗口

当前业务线程里，数据库更新与 MQ 发送并没有被统一收敛为一个可靠的最终一致性模型。

真实场景可能发生：

- Java 把消息发出去了，但后续数据库事务回滚
- Java 数据库落库成功，但 MQ 在发送阶段抖动失败
- Java 线程在“业务已经决定要渲染”和“消息真正安全交付出去”之间宕机

如果不引入专门的投递保障模型，系统就会长期停留在“能跑，但偶尔说不清”的状态。

#### 2. `render_record` 职责混杂

`render_record` 的本意应该是：

- 记录一次渲染尝试
- 对外展示业务层看到的渲染生命周期

但在当前链路下，它又被迫承担“消息是否已经安全投递出去”的语义。这会导致两个问题：

- 业务状态与消息投递状态混在一起，后续很难扩展
- 当投递失败、重试、抢占、回收出现时，很难只靠 `render_record` 表达清楚

#### 3. Remotion 执行现场状态不能直接当业务真相

Remotion 侧当前的 `tasks` 是内存 `Map`，Redis 只是辅助读取缓存，不能把它等价成业务真相源。

真实场景可能发生：

- Remotion 进程重启，内存任务表丢失
- Java 数据库里仍然是 `RENDERING`
- Remotion 却已经“不认识这个任务”

这不是 Remotion 做错了，而是分布式系统里必须接受的现实：

- 执行侧最先知道“现场发生了什么”
- 但业务真相必须由持久化真相源收敛

#### 4. 当前重试、超时、人工重试语义还不完整

如果没有正式方案，下面这些问题都会在后续实现中不断反复：

- MQ 发送失败后是同步重试还是后台重试
- 用户等待时间应该和后台重试时间绑定吗
- 执行超时后系统是否应自动重新渲染
- 用户再次点击“渲染”时，是复用旧记录还是生成新尝试

这些都不是单一代码点能解决的问题，而是需要一整套状态机与职责边界。

### 6.2.3 混沌测试带来的学习价值

前面的混沌测试阶段虽然不是本文的主方案，但给了这次设计很重要的前置认知。

通过 `RabbitMQChaosTest` 和 Toxiproxy 的弱网/断网注入，我们已经验证过：

- RabbitMQ 失败不会只停留在底层 socket 层
- 网络异常会一路被框架翻译成 `ShutdownSignalException`、`TimeoutException`、`AmqpIOException`、`AmqpTimeoutException` 等更上层异常
- 业务代码真正能拿到的，通常已经是框架层异常，而不是裸网络异常

这件事在微服务里非常关键，因为：

- 重试策略是按框架层异常做的
- 熔断判断是按框架层异常做的
- 补偿逻辑也是按业务能感知到的异常边界做的

所以本文后面选择 Outbox、状态机和异步重试，不是“为了追求复杂”，而是因为我们已经验证过：**网络不可靠是常态，业务层必须有一套更稳定的应对模型。**

## 6.3 方案收敛过程与候选方案对比

这一节保留我们多轮讨论的关键痕迹。重点不是展示“我们想过很多”，而是让后续实现者知道：**为什么现在定成这样，而不是别的样子。**

### 6.3.1 业务同步重试 MQ vs Outbox 异步重试

| 问题 | 候选方案 | 选择 | 优点 | 缺点 | 不选原因 |
|---|---|---|---|---|---|
| MQ 发送失败后如何保障投递 | 业务线程内同步重试 MQ | 否 | 实现直观，代码改动少 | 用户请求阻塞，线程长期占用，接口超时风险高，重试风暴会直接放大到用户请求链路 | 用户等待时间不能和最终一致性绑死，微服务里这会迅速恶化吞吐与体验 |
| MQ 发送失败后如何保障投递 | Outbox 异步重试 | 是 | 用户请求可快速返回，重试与产品等待时间解耦，可制度化退避、回收、审计 | 增加表结构与后台投递器复杂度 | 这是控制复杂度后仍能闭环最终一致性的最优折中 |

### 6.3.2 只保留 `render_record` vs `render_record + outbox_message`

| 问题 | 候选方案 | 选择 | 优点 | 缺点 | 不选原因 |
|---|---|---|---|---|---|
| 如何表达业务状态与投递状态 | 只用 `render_record` 一张表 | 否 | 表少，阅读简单 | 投递状态与业务状态混杂，后续很难表达 `PENDING/SENDING/DEAD` 之类语义 | `render_record` 应该描述渲染尝试，不该兼任发件箱全生命周期 |
| 如何表达业务状态与投递状态 | `render_record + outbox_message` 双状态源 | 是 | 职责清晰，便于扩展重试、回收、审计、幂等 | 表结构与状态机变多 | 这是后续多实例投递、排障和演进的基础 |

### 6.3.3 发送失败立刻 `FAILED` vs 保持 `CREATED` 后台重试

| 问题 | 候选方案 | 选择 | 优点 | 缺点 | 不选原因 |
|---|---|---|---|---|---|
| 发件失败时如何更新业务状态 | 立刻把 `render_record` 打成 `FAILED` | 否 | 状态简单，处理直觉化 | 把短时网络抖动直接暴露成业务失败，不利于最终一致性 | 发送失败并不等于渲染业务失败，很多故障只是短暂投递失败 |
| 发件失败时如何更新业务状态 | 保持 `CREATED`，由 Outbox 后台重试 | 是 | 把“任务已创建”和“尚未安全入队”区分开，允许系统自我修复 | 需要引入新的状态解释 | 更符合异步系统真实语义 |

### 6.3.4 长时间重试绑定用户等待 vs 技术时间线与产品时间线拆开

| 问题 | 候选方案 | 选择 | 优点 | 缺点 | 不选原因 |
|---|---|---|---|---|---|
| 用户是否应该同步等待投递重试 | 用户请求一直等到重试完成 | 否 | 从表面看像“用户立刻知道结果” | 高延迟、超时、重复点击、线程占用、吞吐下降 | 这会把系统内部重试成本直接转嫁给用户 |
| 用户是否应该同步等待投递重试 | 用户快速返回，后台重试，前端看状态变化 | 是 | 用户体验可解释，可展示“已创建/投递中/繁忙/失败” | 需要设计状态展示 | 微服务里应拆分“用户响应时长”和“系统最终成功时长” |

### 6.3.5 自动补跑渲染 vs 超时失败后交给用户手动重试

| 问题 | 候选方案 | 选择 | 优点 | 缺点 | 不选原因 |
|---|---|---|---|---|---|
| 执行超时后如何处理 | 系统自动重新投递渲染 | 否 | 用户看起来更“自动恢复” | 会迅速引入重复执行、强幂等、结果覆盖、崩溃续跑等高复杂度问题 | 第一版先收口“最终失败”，不直接解决“自动恢复执行” |
| 执行超时后如何处理 | 直接失败，交给用户手动重试 | 是 | 状态清晰、边界明确、易于排障 | 用户需要再次操作 | 第一版更适合先把失败收口制度化 |

### 6.3.6 用户重试复用旧 `render_record` vs 新建新的 `render_record`

| 问题 | 候选方案 | 选择 | 优点 | 缺点 | 不选原因 |
|---|---|---|---|---|---|
| 用户点击重试时如何建模 | 复用旧 `render_record` | 否 | 表面上记录数更少 | 会把旧失败记录改写，状态与排障信息变脏 | 一次渲染尝试就应该是一条独立记录 |
| 用户点击重试时如何建模 | 新建一条新的 `render_record` | 是 | 每次尝试独立建模，历史完整保留，状态机清晰 | 历史记录会增多 | 最有利于审计、排障和后续统计 |

### 6.3.7 `publisher confirm` 一期引入 vs 标记为二期优化

| 问题 | 候选方案 | 选择 | 优点 | 缺点 | 不选原因 |
|---|---|---|---|---|---|
| 如何定义“消息发送成功” | 一期就引入 RabbitMQ `publisher confirm` | 否 | 语义更严格，可收紧 Broker 确认边界 | 会显著提高一版复杂度，需要补更多发布确认处理逻辑 | 一期先跑通 Outbox 主链路，先解决大问题 |
| 如何定义“消息发送成功” | 一期先以 `convertAndSend()` 成功返回视为成功 | 是 | 简化实现，先聚焦最终一致性主链路 | 语义不是最强，存在确认边界 | 可接受的一版工程折中，后续可升级 |

### 6.3.8 Remotion 直接写业务库 vs Java 做真相源

| 问题 | 候选方案 | 选择 | 优点 | 缺点 | 不选原因 |
|---|---|---|---|---|---|
| 谁来维护业务真相状态 | Remotion 直接写 Java 业务库 | 否 | 看起来链路更短 | Node 服务侵入业务库边界，权限与耦合升高，状态冲突更难治理 | 违背服务边界，后续治理成本高 |
| 谁来维护业务真相状态 | Java 继续做真相源，Remotion 只回写现场状态 | 是 | 职责清晰，便于状态机控制、鉴权、幂等和回调治理 | 需要额外定义回写契约 | 更符合微服务的边界设计 |

### 6.3.9 为什么不是“为了省事”才延期二期项

本次明确延期的能力，比如 `publisher confirm`、回调事件表、消费端更强幂等、Remotion 任务持久化，并不是因为它们不重要，而是因为一版必须先优先解决下面这条主线：

```text
任务创建成功
  ->
消息最终可安全重试投递
  ->
业务状态能与执行状态解耦
  ->
任务失败能明确收口
  ->
用户可手动重新发起下一次尝试
```

如果一开始就把所有增强能力同时纳入，一版很容易失去焦点，最后既没有闭环最终一致性，也没有形成清晰的二期演进路径。

## 6.4 第一期定稿方案

### 6.4.1 总原则

第一版方案明确采用以下原则：

1. Java 是业务真相源
2. Remotion 是执行现场源
3. Outbox 解决消息投递一致性
4. 状态机解决跨服务状态推进
5. 用户等待时间与后台最终一致性时间解耦

对应地，系统职责边界如下：

```text
Java
  - 负责业务状态真相
  - 负责 Outbox 持久化与投递保障
  - 负责收敛回调、轮询、超时与人工重试语义

Remotion
  - 负责真正执行渲染
  - 负责产生 STARTED / SUCCEEDED / FAILED 等现场状态
  - 不负责成为最终业务真相源
```

### 6.4.2 第一版目标链路

```text
用户点击“渲染”
   ->
Java 在同一业务事务内：
  - 创建 render_record(status=CREATED)
  - 创建 outbox_message(status=PENDING)
   ->
接口快速返回 renderId
   ->
Dispatcher 扫描 PENDING outbox
   ->
抢占发送权，执行 MQ 投递
   ->
投递成功：outbox -> SENT，render_record -> QUEUED
   ->
Remotion 开始执行并回写 STARTED
   ->
Java 推进 render_record -> RENDERING
   ->
Remotion 回写 SUCCEEDED / FAILED
   ->
Java 推进 render_record -> DONE / FAILED
```

### 6.4.3 `render_record` 状态机

第一版 `render_record` 状态如下：

| 状态 | 含义 | 是否终态 |
|---|---|---|
| `CREATED` | 任务已在业务库中创建，但尚未确认入队 | 否 |
| `QUEUED` | Outbox 已确认投递成功，任务已进入渲染队列 | 否 |
| `RENDERING` | Remotion 已实际开始执行渲染 | 否 |
| `DONE` | 渲染成功，结果已可用 | 是 |
| `FAILED` | 渲染链路已明确失败，需要人工重试 | 是 |

约束如下：

- `CREATED` 是本次方案新增的关键状态
- `DONE` 与 `FAILED` 都是终态
- 终态不可逆，禁止 `DONE -> FAILED` 或 `FAILED -> DONE`

### 6.4.4 `outbox_message` 状态机

第一版 Outbox 状态如下：

| 状态 | 含义 | 是否终态 |
|---|---|---|
| `PENDING` | 等待投递 | 否 |
| `SENDING` | 某个 Dispatcher 实例已抢到发送权，正在发送 | 否 |
| `SENT` | 已按一版判定规则视为发送成功 | 是 |
| `DEAD` | 达到重试上限，停止自动投递 | 是 |

这里要特别强调：

- `SENDING` 不是终态
- `SENDING` 只是“持有发送权”的临时状态
- 如果实例在 `SENDING` 阶段崩溃，消息必须有机会被回收并重新进入 `PENDING`

### 6.4.5 第一版 `outbox_message` 必需字段

第一版先只保留跑通主链路所必需的字段：

| 字段 | 作用 |
|---|---|
| `id` | 主键 |
| `message_id` | 消息全局唯一标识 |
| `message_type` | 消息类型，例如 `RENDER_SUBMIT` |
| `biz_key` | 业务键，当前建议使用 `renderId` |
| `payload` | 实际投递到 MQ 的消息体 |
| `status` | `PENDING/SENDING/SENT/DEAD` |
| `retry_count` | 已失败重试次数 |
| `next_retry_at` | 下次允许重试的时间点 |
| `last_error` | 最近一次失败原因 |
| `created_at` | 创建时间 |
| `updated_at` | 更新时间 |

这一版先不引入更重的治理字段，是为了先把最终一致性主链路闭环。

### 6.4.6 Dispatcher 规则

Dispatcher 的核心目标只有一个：

**同一条 Outbox 消息，在任意时刻只能有一个投递器真正去发。**

第一版规则如下：

1. 定时扫描 `status = PENDING and next_retry_at <= now`
2. 扫描到消息后，不能直接发送，必须先抢发送权
3. 抢发送权通过条件更新完成，而不是仅靠代码内判断
4. 只有抢占成功的实例，才允许执行 MQ 投递
5. 发送成功后：`SENDING -> SENT`
6. 发送失败后：
   - 还可重试：`SENDING -> PENDING`
   - 超过上限：`SENDING -> DEAD`
7. `SENDING` 超过超时窗口仍未结束，自动回收回 `PENDING`

伪流程如下：

```text
scan PENDING where next_retry_at <= now
   ->
try update status = SENDING where id = ? and status = PENDING
   ->
if update success:
    send MQ
    if success:
        status = SENT
    else if retryable:
        status = PENDING
        retry_count += 1
        next_retry_at = ...
    else:
        status = DEAD
```

### 6.4.7 第一版重试与产品时间线

这一轮讨论里最重要的收敛之一，是把**技术时间线**和**产品时间线**拆开。

#### 技术时间线

系统为了最终一致性，会在后台重试 Outbox 投递。

#### 产品时间线

用户不应该同步等待这些重试全部结束。用户应该：

- 点击渲染后快速拿到 `renderId`
- 通过状态看到“已创建、投递中、繁忙、失败”
- 在明确失败后决定是否手动重试

第一版约束：

- 用户点击渲染后接口快速返回
- `120s` 内仍未成功入队，视为用户可感知失败

推荐的一版退避策略：

| 次数 | 建议等待 |
|---|---|
| 首次创建 | 立即尝试 |
| 第 1 次失败后 | `10s + 随机 0~3s` |
| 第 2 次失败后 | `20s + 随机 0~5s` |
| 第 3 次失败后 | `30s + 随机 0~8s` |
| 第 4 次失败后 | `60s + 随机 0~10s` |

这类“递增重试 + jitter”的设计目的有两个：

- 给短时网络抖动恢复机会
- 避免大量任务在同一秒集体重试，形成重试风暴

### 6.4.8 Remotion 回写契约

第一版只保留最小闭环状态，不急着引入更复杂的进度和心跳协议。

#### 一期状态

- `STARTED`
- `SUCCEEDED`
- `FAILED`

#### 最小回写字段

| 字段 | 用途 |
|---|---|
| `eventId` | 回写事件唯一标识，用于幂等 |
| `renderId` | 对应哪一次渲染尝试 |
| `status` | `STARTED/SUCCEEDED/FAILED` |
| `occurredAt` | 状态实际发生时间 |
| `outputUrl` | 成功时返回产物地址 |
| `errorCode` | 失败时的错误码 |
| `errorMessage` | 失败时的错误信息 |

#### 状态推进规则

Java 侧收敛状态时遵循：

- 收到 `STARTED`：
  - `QUEUED -> RENDERING`
  - 如仍是 `CREATED`，允许自愈推进到 `RENDERING`
  - 若已是终态，拒绝回退
- 收到 `SUCCEEDED`：
  - `QUEUED/RENDERING -> DONE`
  - 保存 `outputUrl`
- 收到 `FAILED`：
  - `QUEUED/RENDERING -> FAILED`
  - 保存错误信息

第一版明确采用：

- 回调作为主路径
- 轮询作为兜底路径

这意味着即使回调丢失，Java 也必须有能力通过轮询或超时规则继续收口状态。

### 6.4.9 失联与超时收口

一个关键认识是：

**Remotion 的执行现场状态可以丢，但 Java 的业务真相状态不能失控。**

因此第一版接受以下现实：

- Remotion 重启后，内存任务表可能丢失
- Java 不要求 Remotion 一期具备“崩溃后续跑恢复”
- Java 通过回调、轮询、超时规则来维护真相收口

第一版超时原则：

| 状态 | 超时含义 | 处理策略 |
|---|---|---|
| `QUEUED` 长时间未进入 `RENDERING` | 可能未被消费、回调丢失或消费侧异常 | 超时后 `FAILED` |
| `RENDERING` 长时间未结束 | 可能执行卡死、进程崩溃、现场状态丢失 | 超时后 `FAILED` |

第一版明确不做：

- 执行超时后自动补跑
- Remotion 崩溃后继续从中间状态恢复渲染

原因不是这些能力不重要，而是一期先把“失败能够明确落地”做扎实，比一开始就追求“自动自愈补跑”更稳。

### 6.4.10 用户手动重试语义

第一版明确采用：

- 用户手动重试时，**新建一条新的 `render_record`**

这样做的原因：

- 每次渲染尝试是独立事件
- 历史失败记录可以完整保留
- 不需要把旧 `FAILED` 记录改回运行态
- 有利于后续审计、统计与排障

因此一个项目在模型上应允许：

- 一个 `project`
- 对应多条 `render_record`
- 其中“最新一次尝试”作为当前对外展示的主要状态

## 6.5 为什么不这么做

这一节专门承接被否决方案，避免后续实现阶段重新回到已经讨论过的岔路。

### 6.5.1 为什么不继续让业务线程同步重试 MQ

如果把重试放在用户请求线程里，会有直接后果：

- 用户等待时间不可控
- 接口超时风险升高
- 服务线程长时间占用
- 网络抖动时吞吐量快速下降
- 用户因误以为失败而重复点击，进一步制造重复请求

这不符合微服务系统对高抖动场景的处理方式。

### 6.5.2 为什么不让 `render_record` 单表承担所有语义

单表方案的最大问题不是“现在不能写”，而是“后面很难长大”。

一旦进入多实例 Dispatcher、回收、重试、排障阶段，你很快就会需要：

- 哪条消息待发送
- 哪条消息正在被某个实例占用
- 哪条消息已经进入死亡状态

这些都不是 `render_record` 应该承担的主职责。

### 6.5.3 为什么一期不做自动补跑

自动补跑看起来用户体验更强，但真正引入时会立即牵出更多决策：

- 如何避免重复渲染
- 如何界定“上一次尝试其实还在跑”
- 如何处理重复结果覆盖
- 是否需要消费端更强幂等
- Remotion 是否要支持断点续跑

如果这些问题没有一起回答，自动补跑只会把不确定性从“失败”变成“重复执行”。

### 6.5.4 为什么 Remotion 不能直接成为真相源

Remotion 确实最先知道“执行现场发生了什么”，但它不适合直接成为业务真相源：

- 当前状态主要在内存，天然不稳定
- 服务重启时现场状态可丢
- 让 Node 服务直接写业务库会增加耦合和权限风险
- 多个状态来源同时改业务表，会提高状态冲突和排障复杂度

因此更合理的职责划分是：

- Remotion 产出现场状态
- Java 收敛业务真相

## 6.6 二期优化路线

下面这些能力已经在本轮讨论中明确识别出来，但为了控制一版复杂度，暂时不纳入第一版实现。它们不是“可有可无”，而是**已经排入后续演进路线**。

### 6.6.1 RabbitMQ `publisher confirm`

**价值：**

- 可把“发送成功”的语义从“调用成功返回”收紧到“Broker 明确认收”
- 能进一步降低发布确认边界的不确定性

**为什么一期先不做：**

- 一期先解决 Outbox 主链路与状态机主问题
- 引入发布确认会显著增加发送确认与失败处理复杂度

### 6.6.2 Outbox 增强字段

建议二期补充：

- `exchange_name`
- `routing_key`
- `payload_version`
- `sent_at`
- `last_attempt_at`
- `lock_owner`

**价值：**

- 增强排障能力
- 提高协议演进能力
- 在多实例投递器下提高可观测性

**为什么一期先不做：**

- 一期的 11 个核心字段已经足够支撑功能闭环
- 先把复杂度留给真正需要它的阶段

### 6.6.3 回调幂等专用 `inbox_event` / `callback_event` 表

**价值：**

- 更稳定地处理重复回调、乱序回调与审计需求
- 让回调侧也具备类似 Inbox 模式的持久化能力

**为什么一期先不做：**

- 一期先用 `eventId + 状态机单向推进` 做轻量幂等
- 避免同时引入第二套事件持久化模型

### 6.6.4 更强的消费端幂等

候选增强方向：

- Redis 抢执行权
- 持久化幂等真相
- Java 侧执行申请接口

**价值：**

- 更强地防止重复消费、重复执行
- 为自动补跑或多实例执行提供基础

**为什么一期先不做：**

- 当前一版已经明确“执行失败交给用户重试”，不强依赖自动补跑
- 消费端幂等一旦做强，往往会连带引入更复杂的回写和执行治理

### 6.6.5 Remotion 任务状态持久化

候选方向：

- Redis 真正成为任务状态层
- Remotion 自己落数据库任务表
- Java 与 Remotion 共享更明确的任务同步协议

**价值：**

- 降低 Remotion 重启后现场状态丢失的影响
- 为进度、心跳、恢复执行打基础

**为什么一期先不做：**

- 一期已经接受“执行现场会丢，Java 负责超时收口”
- 先解决真相收口，再增强执行侧持久化

### 6.6.6 更丰富的状态协议

候选状态：

- `PROGRESS`
- `HEARTBEAT`
- `CANCELLED`
- `PARTIAL_SUCCESS`

**价值：**

- 前端体验更细腻
- 更容易区分“慢”和“死”

**为什么一期先不做：**

- 一期先打通 `STARTED / SUCCEEDED / FAILED` 主闭环
- 状态越丰富，状态机冲突和幂等治理成本越高

### 6.6.7 自动补跑与崩溃续跑

**价值：**

- 用户感知更“自动恢复”
- 系统具备更强的执行自治能力

**为什么一期先不做：**

- 需要更强的消费端幂等
- 需要更强的执行态持久化
- 需要明确重复结果、重复计费和任务占用模型

### 6.6.8 更完整的观测与告警

候选方向：

- Outbox 积压量监控
- `SENDING` 超时回收次数监控
- `DEAD` 消息告警
- 渲染超时率、失败率、平均时长指标

**价值：**

- 让系统从“能解释”走向“能运营”
- 便于长期治理与扩容

**为什么一期先不做：**

- 一期先完成可靠性语义定稿与主链路落地
- 观测体系可以在第二阶段伴随实现逐步补齐

## 6.7 状态机总览

| 维度 | 状态 | 含义 | 备注 |
|---|---|---|---|
| `render_record` | `CREATED` | 业务任务已创建，尚未确认入队 | 新增状态 |
| `render_record` | `QUEUED` | 已确认进入渲染队列 | 等待执行 |
| `render_record` | `RENDERING` | Remotion 已开始执行 | 执行中 |
| `render_record` | `DONE` | 渲染成功 | 终态 |
| `render_record` | `FAILED` | 渲染失败 | 终态 |
| `outbox_message` | `PENDING` | 待发送 | 初始状态 |
| `outbox_message` | `SENDING` | 正在由某实例发送 | 可回收 |
| `outbox_message` | `SENT` | 视为已发送成功 | 终态 |
| `outbox_message` | `DEAD` | 达到重试上限 | 终态 |

## 6.8 实施顺序建议

为避免实现过程中再次发散，建议按以下顺序推进：

1. **数据模型**
   - 引入 `outbox_message`
   - 为 `render_record` 增加 `CREATED` 语义

2. **Dispatcher**
   - 定时扫描
   - 抢占发送权
   - 失败退避
   - `SENDING` 超时回收

3. **状态推进**
   - 发件成功推进 `CREATED -> QUEUED`
   - Remotion 回写推进 `QUEUED -> RENDERING -> DONE/FAILED`
   - 执行超时推进失败收口

4. **回调 / 轮询兜底**
   - 回调作为主路径
   - 保留轮询兜底与状态自愈能力

5. **前端状态展示**
   - 展示“已创建、正在入队、系统繁忙、失败可重试”
   - 不让用户同步等待后台重试完成

6. **二期扩展**
   - `publisher confirm`
   - 回调事件表
   - 更强幂等
   - Remotion 状态持久化
   - 自动补跑
   - 观测与告警

## 6.9 结论

本轮方案的本质，不是简单把“MQ 再包一层表”，而是正式把渲染链路从“能跑的异步调用”推进到“有边界、有状态、有失败收口的微服务可靠性模型”。

第一版最重要的不是把所有高级能力一次做满，而是明确下面这条主线：

```text
任务创建成功
  ->
消息可靠投递
  ->
业务状态与执行状态解耦
  ->
故障可重试
  ->
失败可收口
  ->
用户可发起下一次独立尝试
```

这条主线一旦成立，Outbox、幂等、状态机、回调治理、执行恢复这些能力才有稳定的演进基础。
