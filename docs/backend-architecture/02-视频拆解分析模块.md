# 批次 2：视频拆解分析模块

## 2.1 模块职责

接收用户上传的样例视频，通过 FFmpeg + LLM 协作完成以下拆解：
- **基础信息提取**：时长、分辨率、帧率、封面、音轨信息
- **镜头切分**：检测场景切换点，将视频拆成多个镜头片段
- **三类结构分析**：脚本结构、节奏结构、包装结构
- **语音/字幕提取**：ASR 转写 + 硬字幕 OCR

> [!IMPORTANT]
> P0 采用**每视频一任务**建模：`POST /videos/upload` 返回单个 `taskId`，`POST /videos/upload/batch` 返回 `taskIds[]`。多样例融合发生在模板提取阶段，不在拆解阶段复用同一 `taskId`。

## 2.2 整体处理流程

```
用户上传视频
     │
     ▼
┌──────────────┐
│ MediaProber  │ ── FFmpeg probe ──► 基础元信息（时长/分辨率/帧率/编码）
└──────┬───────┘
       │
       ▼
┌──────────────────────────────────────────────────┐
│           并行处理（异步，互不依赖）                │
│                                                  │
│  ┌─────────────┐  ┌────────────┐  ┌───────────┐  │
│  │SceneDetector│  │ ASR Engine │  │ 关键帧    │  │
│  │ 镜头切分    │  │ 语音转写+  │  │ Hook锁定  │  │
│  │ +sceneScore │  │ 音频语义   │  │ 抽帧(≤5) │  │
│  └──────┬──────┘  └─────┬──────┘  └─────┬─────┘  │
│         │               │              │         │
└─────────┼───────────────┼──────────────┼─────────┘
          ▼               ▼              ▼
     镜头切点数组    逐句文本+时间戳   核心 Hook 代表帧
     +sceneScore     +语义标签        (严格≤5张)
          │               │              │
          ▼               ▼              ▼
   ┌────────────────────────────────────────────┐
   │  TimelineMatcher（多路时间轴归一器）        │
   │  Java层完成时序对齐，输出统一JSON文本流      │
   └────────────────────┬───────────────────────┘
                        │
                        ▼ 多模态时序日志 JSON
             ┌────────────────────┐
             │ LLM StructureAnalyzer │
             │ 综合分析三类结构       │
             └──────────┬─────────┘
                        │
                        ▼
                结构化 JSON 输出
                (存入模板/返回前端)
```

> [!IMPORTANT]
> **为什么需要 TimelineMatcher？** 并行阶段产出的镜头切点、ASR 文本、音频语义是三条独立时间轴。如果直接把零散数据甩给 LLM，模型无法稳定对齐“某句台词对应什么声音环境与画面变化”。TimelineMatcher 在 Java 层按时间窗口做多路归并，输出一条统一的时序日志，大幅降低 LLM 的理解负担。

### 2.3.2 SceneDetector — 镜头切分

**方案选择：**

| 方案 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| FFmpeg `select` 滤镜 | 帧间差异检测 | 零依赖，纯 FFmpeg | 阈值需调优 |
| PySceneDetect 调用 | 内容感知检测 | 精度高 | 需 Python 环境 |
| LLM 视觉分析 | 抽帧后让 LLM 判断 | 理解语义 | 成本高、速度慢 |

**推荐方案：FFmpeg `scdet` 滤镜（P0 阶段）**

为了支持后期的低成本调优与懒加载架构（详见 2.5.0 节），FFmpeg 此时作为一个“暴力物理特征提取器”，我们会固定传入极低的敏感阈值（如 `0.1` 对应的 `10`），暴露全片所有微小异动，全量保存它们的真实 `sceneScore`。

```bash
# 检测场景切换点，并输出时间戳和真实的场景变动分数（-an 禁用音频处理提速）
ffmpeg -v info -i input.mp4 -an -vf "scdet=threshold=10,metadata=print:file=-" -f null -
```
*(日志将输出 `lavfi.scd.time` 和 `lavfi.scd.score`，非常便于 Java 层解析)*

> [!WARNING]
> 必须加 `-an` 参数！不加的话 FFmpeg 会同时处理音频流重采样，镜头切分速度慢一倍。

**输出数据结构（每个镜头）：**
```json
{
  "shotIndex": 0,
  "startTime": 0.0,
  "endTime": 3.2,
  "duration": 3.2,
  "sceneScore": 0.47,
  "thumbnailPath": "/data/tasks/{taskId}/shots/shot_000.jpg"
}
```

> [!NOTE]
> `sceneScore` 是 FFmpeg `select` 滤镜输出的帧间差异值（0~1），用于后续 Hook 锁定抽帧时按画面变动强度排序。

### ~~2.3.2b AudioPeakDetector~~ (已废弃)

> [!WARNING]
> **已废弃**：FFmpeg astats 信号处理方案已迁移至 ASR 线程。音频语义分析由 LLM 在逐句转写时同步输出 `audioEmotion` / `volumeIntensity` / `backgroundEnvironment` 三个语义标注字段，详见 2.4 节。
>
> **迁移理由**：FFmpeg astats 输出 dB 数值需额外 Java 峰值检测算法和类型推断，而 LLM 可直接输出语义级判断（如"情绪激昂 + 有垫乐"），对后续结构分析更直接可用。




### 2.3.3 关键帧抽取 — 核心前置与 Hook 锁定法

> **Token 刺客警告**：一条 30s 视频通常切出 8~10 个镜头，若每个镜头都抽帧塞给 LLM，会瞬间产生几十张图片。Doubao-lite 的多模态上下文窗口扛不住，Token 费用也会爆炸。因此必须极度克制抽帧数量。

**触发时机前置红利：**
由于采用了“高敏提取 + 语义后置过滤”，抽帧动作必须在 **高敏提取（Stage 2）完成后立即进行**。即便高敏模式切出了 50 个微小片段，其第一个片段依然是真正的开场，且其 `sceneScore` 前 3 的片段依然代表了全片变动最剧烈的画面。提前抽帧，意味着 TimelineMatcher 进行参数寻优时无需再去跑 FFmpeg 抽帧，真正实现调优 0 成本。

**核心原则：不管视频多长，总抽帧数量严格封顶 5 张。**

**抽帧命令：**
```bash
# -an 禁用音频，加速抽帧
ffmpeg -ss {targetTime} -i input.mp4 -an -frames:v 1 -q:v 2 frame_{index}.jpg
```

**Hook 锁定抽帧策略：**

| 帧编号 | 来源 | 抽帧位置 | 目的 |
|--------|------|----------|------|
| 帧 1 | 第 1 个镜头（Hook 槽位） | 首帧（0.1s 偏移） | 捕捉黄金 3 秒的开幕视觉 |
| 帧 2 | 第 1 个镜头（Hook 槽位） | 中间帧 | 完整理解 Hook 表达方式 |
| 帧 3~5 | 剩余所有镜头 | sceneScore 最高的 Top3 时间点各取 1 帧 | 覆盖中后段最剧烈的画面变动 |

**Java 伪代码逻辑：**
```java
// 1. Hook 槽位：第一个镜头强制抽 2 帧
Shot hookShot = shots.get(0);
frames.add(extractFrame(hookShot.startTime + 0.1)); // 首帧
frames.add(extractFrame(hookShot.midTime()));       // 中帧

// 2. 剩余镜头按 sceneScore 降序，取 Top3
List<Shot> rest = shots.subList(1, shots.size());
rest.sort((a, b) -> Double.compare(b.sceneScore, a.sceneScore));
for (int i = 0; i < Math.min(3, rest.size()); i++) {
    frames.add(extractFrame(rest.get(i).midTime()));
}
// 最终 frames.size() <= 5，Token 消耗骤降 80%
```

**收益分析：**
- 大模型既看清了开头怎么吸睛，又看清了中后段最剧烈的画面变化
- Token 消耗从「每镜头 1~3 帧 × 10 镜头 = 10~30 帧」降至固定 5 帧
- 对 Doubao-lite 的上下文窗口友好，不会触发 Context Limit

所有帧存储到 `/data/tasks/{taskId}/frames/`

```json
  },
  {

    "start": 3.5,
    "end": 5.0,
    "audioEmotion": "NONE",
    "volumeIntensity": "HIGH",
    "backgroundEnvironment": "MUSIC_FX",
    "vocalVibe": "",
    "bgmGenre": "悬疑底噪",
    "bgmInstruments": "脉冲低音与金属打击音"
  }
]
```

**音频语义标注字段说明：**

| 字段 | 类型 | 枚举值 | 说明 |
|------|------|--------|------|
| `audioEmotion` | STRING | `CALM` / `CURIOUS` / `AGITATED` / `EXCITED` / `URGENT` / `NONE` | 说话者语气情绪。无人声时为 `NONE` |
| `volumeIntensity` | STRING | `LOW` / `MEDIUM` / `HIGH` / `PEAK` | 该时间段的整体音量强度（含人声+背景音） |
| `backgroundEnvironment` | STRING | `MUSIC` / `FX` / `MUSIC_FX` / `NOISE` / `SILENT` | 背景声音环境定性 |
| `vocalVibe` | STRING | 自然语言 | 语音基调描述。无人声时为空字符串 |
| `bgmGenre` | STRING | 自然语言 | 背景音乐流派。无音乐时为空字符串 |
| `bgmInstruments` | STRING | 自然语言 | 主导乐器组合。无音乐时为空字符串 |

**`backgroundEnvironment` 枚举详解：**
- `MUSIC`：有垫乐/BGM（最常见于营销类和剪辑类视频）
- `FX`：有特殊音效（如大笑声、拍桌声、转场音效等）
- `MUSIC_FX`：垫乐与特殊音效并存且都明显可感知
- `NOISE`：纯环境噪音（如街道声、风声，常见于探店/实拍类）
- `SILENT`：安静人声，无明显背景音

> [!TIP]
> **无人声片段的处理**：当某时间段没有人声（如纯 BGM 段落），ASR 仍应输出一条 `text` 为空的记录，但 `backgroundEnvironment` 和 `volumeIntensity` 必须填充，避免时序黑洞。

> [!NOTE]
> `MUSIC_FX` 已纳入当前枚举，用于表达“BGM + 特效音并存”的复合场景。

## 2.5 LLM 结构分析

### 2.5.0 TimelineMatcher — 多路时间轴归一器

TimelineMatcher 是 LLM 之前的**必经中转站**，在 Java 层完成多路数据的时序对齐。

**输入三路数据：**
1. SceneDetector 产出：镜头切点数组 + sceneScore（纯视觉维度）
2. ASR 产出：逐句文本 + 起止时间戳 + **音频语义标注**（`audioEmotion` / `volumeIntensity` / `backgroundEnvironment` / `vocalVibe` / `bgmGenre` / `bgmInstruments`）
3. 关键帧抽取产出：≤5 张帧的时间点与文件路径

> [!IMPORTANT]
> **时序矛盾破局：高敏提取 + 语义后置过滤 (Post-Filtering)**
> 按照流水线，FFmpeg (Stage 2) 执行时并不知道视频属于什么品类，自然拿不到品类专属的切分阈值。
> **巧妙的解决方案**：
> 1. **全量高敏提取**：`SceneDetector` 采用极低阈值 (如 0.1) 提取并保存全量微小画面的变动与原始 `sceneScore`。
> 2. **阈值懒加载**：LLM (Stage 3) 识别出品类后，顺带获取该品类的最佳阈值（如 `0.4` 或 `0.25`，可由品类字典库提供或 LLM 自主推断）。
> 3. **内存级后处理**：`TimelineMatcher` 在组合时间轴前，直接在内存中用这个真实阈值对高敏镜头列表进行**剔除与相邻合并**（抛弃 `sceneScore < 真实阈值` 的伪切点）。
> 
> **最大红利**：未来引入 Chroma 写脚本跑几万个视频去自动寻优“最佳阈值”时，**永远不需要去重跑沉重的 FFmpeg**！只需用新阈值纯内存过滤已存好的 `scene_result.json`，调优成本降至 0！

**对齐策略：**
```text
对于每个后置过滤后合并的真实镜头时间窗口 [shotStartTime, shotEndTime]：
  1. 收集落在该窗口内的所有 ASR 语句（按 startTime 起点归属）
  2. 收集落在该窗口内的音频语义事件（emotion / volume / environment）
  3. 标记该窗口是否有关键帧被抽取
  4. 合并为一条时序事件记录
```

> [!IMPORTANT]
> 时间归属统一采用半开区间：普通段为 `[start, end)`，最后一段为 `[start, end]`。
> 该规则同时应用于 ASR 与关键帧，避免边界重复与“最后一段吞全量关键帧”。

> [!IMPORTANT]
> 高敏切分后会执行碎段提纯：当 segment 时长低于 `timeline.min-segment-duration-sec`（默认 `0.60s`）且不含关键帧时，优先并入前一段（无前段则并入后一段）。
> 通过该后置合并机制可显著降低 0.x 秒碎片段，提升时间轴可读性。

**输出：多模态时序日志（JSON 数组）**
```json
[
  { "time": "0.0s - 3.2s", "shotIndex": 0, "type": "SHOT+ASR",
    "content": "[镜头0] sceneScore=0.47 | ASR: '大一早八顶不住？'" },
  { "time": "1.2s", "type": "ASR_SEMANTIC",
    "content": "ASR语义: emotion=EXCITED | volume=PEAK | env=MUSIC_FX" },
  { "time": "3.2s - 12.0s", "shotIndex": 1, "type": "SHOT+ASR",
    "content": "[镜头1] sceneScore=0.31 | ASR: '纯正手作咖啡，拯救你的困意...'" },
  { "time": "8.5s", "type": "PHYSICAL_ANOMALY",
    "content": "画面剧烈抖动(0.52) — 可能为特效强调" }
]
```

> [!TIP]
> `PHYSICAL_ANOMALY` 是指非镜头切换的画面骤变（如闪白、缩放特效、抖动强调）；音频侧强调点通过 `ASR_SEMANTIC` 表达，不再依赖波峰信号。

**不再把零散数据直接甩给 LLM**，而是将 TimelineMatcher 输出的多模态时序日志作为标准输入。

**LLM 输入协议（文本契约）：**
```
你现在是短视频结构拆解专家。请阅读 Java 系统为你多路对齐后的【样例视频多模态时序日志】：

--- 视频基础信息 ---
时长: 30.5s | 分辨率: 1080x1920 | 镜头数: 8 | 品类: 营销类

--- 多模态时序日志 ---
[
  { "time": "0.0s - 3.2s", "type": "SHOT+ASR", "content": "..." },
  { "time": "1.2s", "type": "ASR_SEMANTIC", "content": "..." },
  ...
]

--- Hook代表帧描述（共5张） ---
帧1(0.1s): 画面中央大字"早八人自救指南"，背景暗色
帧2(1.6s): 手持咖啡杯特写，蒸汽上升
...

请对照系统已有的营销特效字典进行定性分析。
如果发现不在字典中的新特效，请在 "adaptive_props" 这个 Map 中自主发明新字段进行扩写！

输出 JSON 格式...
```

> [!IMPORTANT]
> 关键帧不以图片形式直接传入（避免 Token 爆炸），而是由 Java 层对帧图片做简要文本描述后拼入 Prompt。若后续切换到支持视觉的 LLM（如 GPT-4o），可将 ≤5 张帧图以 base64 传入。

### 2.5.2 三类结构分析 Prompt 策略

**脚本结构分析 Prompt 要点：**
```
请分析以下视频的脚本结构，识别出：
1. 开头钩子(Hook)：吸引观众的方式（提问/悬念/冲突/数据）
2. 中段展开：卖点展示顺序、论证方式
3. 结尾CTA：引导行动的方式（关注/购买/评论）
4. 每个段落对应的镜头区间

输出 JSON 格式，字段如下...
```

**节奏结构分析 Prompt 要点：**
```
请分析以下视频的节奏特征：
1. 镜头切换频率（快/中/慢，每秒切换次数）
2. 高潮位置（哪个时间段节奏最密集）
3. 段落快慢变化曲线
4. BGM 踩点提示（结合镜头切换时间点）

输出 JSON 格式...
```

**包装结构分析 Prompt 要点：**
```
请分析以下视频的视觉包装特征：
1. 字幕风格（位置/字号/颜色/动效）
2. 标题条/卖点卡片的出现时机
3. 贴纸/表情包的使用方式
4. 转场类型（硬切/溶解/滑动/缩放）
5. 封面风格描述

输出 JSON 格式...
```

> [!NOTE]
> Prompt 模板统一由 `PromptBuilder` 管理，存储在资源文件或数据库中，便于迭代优化。不同品类可有不同的 Prompt 变体。
> 当前代码实现中，方舟相关提示词统一收敛在 `ArkPromptTemplates` 模板类，避免各引擎重复硬编码。

### 2.5.3 LLM 调用流程

```
PromptBuilder 构造 prompt
        │
        ▼
   LlmClient 发起调用
        │
        ├── 正常响应 ──► 解析 JSON ──► 校验 Schema ──► 返回结构数据
        │
        ├── JSON 格式错误 ──► 自动重试（追加"请严格输出JSON"提示，最多2次）
        │
        └── 超时/异常 ──► 记录日志 ──► 标记该分析维度为 FAILED ──► 不阻塞其他维度
```

**关键设计：**
- 三类结构分析**可并行调用** LLM（3 个独立请求）
- 每次调用独立超时，单个失败不影响整体
- LLM 返回结果需通过 JSON Schema 校验，不合规则重试
- 任务完成态判定：若至少一个维度成功且可产出模板抽取所需主干字段，则状态可为 `COMPLETED`，并在结果中记录 `partialFailedDimensions`

## 2.8 开发者扩展点

1. **镜头切分精度**：`scene` 阈值可按品类从知识库读取，也可暴露 API 让用户微调后重新切分
2. **LLM 模型切换**：`LlmClient` 抽象接口，开发时用 Doubao-lite + 文本描述帧，后续可切 GPT-4o 直接传入 ≤5 张帧图做真正的视觉分析
3. **分析维度扩展**：新增第四类结构（如"情感曲线"）只需新增 Prompt 模板 + Analyzer 实现
4. **抽帧上限可调**：当前 Hook 锁定法封顶 5 帧，若切换到大上下文窗口模型，可适当放宽到 8~10 帧
5. **TimelineMatcher 对齐窗口**：当前按镜头切点分窗口，后续可改为滑动窗口或基于 ASR 语句边界分窗口
6. **物理异动字典**：`PHYSICAL_ANOMALY` 的检测阈值和类型可持续扩展（闪白、抖动、缩放、滤镜切换等）
