## 4.2 数据库表设计

### 4.2.0 全局主键与素材隔离规范

**业务主键规范（强制）：**
- 所有业务表统一新增 `biz_id BIGINT UNSIGNED NOT NULL`，作为业务主键，值由雪花算法生成
- 所有 `biz_id` 均需唯一索引（`UNIQUE`）
- 原有 `id` 保留为数据库内部自增主键，用于聚簇索引和物理存储
- 对外接口、跨服务消息、审计日志优先使用 `biz_id`

> 为避免重复，后续各表字段清单若未重复展示 `biz_id`，默认均按本规范补齐并建立唯一索引。

**素材物理隔离规范（强制）：**
- 拆解流仅落 `analysis_video_material`（仅视频）
- 创作流仅落 `creative_material`（文案/图片/视频）
- 两库禁止混写；迁移编排仅引用 `creative_material`，拆解任务仅引用 `analysis_video_material`

### 4.2.1 video_analysis_task（视频拆解任务）

| 字段名 | 数据类型 | 约束 | 说明 |
|--------|----------|------|------|
| `id` | BIGINT UNSIGNED | PK, AUTO_INCREMENT | 主键 |
| `biz_id` | BIGINT UNSIGNED | UK, NOT NULL | 业务主键（雪花 ID） |
| `task_id` | VARCHAR(36) | UK, NOT NULL | 任务标识（兼容现有 API） |
| `source_video_biz_id` | BIGINT UNSIGNED | FK, NOT NULL | 拆解视频素材业务主键（关联 analysis_video_material.biz_id） |
| `status` | VARCHAR(20) | NOT NULL, DEFAULT 'PENDING' | 任务状态：PENDING / PROCESSING / ANALYZING / COMPLETED / FAILED / CANCELED |
| `progress` | TINYINT UNSIGNED | NOT NULL, DEFAULT 0, CHECK(0-100) | 进度百分比 0~100 |
| `progress_step` | VARCHAR(50) | NULL | 当前步骤描述 |
| `source_file_path` | VARCHAR(500) | NOT NULL | 原始视频文件路径快照（审计用） |
| `file_size` | BIGINT UNSIGNED | NULL | 文件大小（字节） |
| `error_message` | TEXT | NULL | 失败时的错误信息 |
| `error_step` | VARCHAR(50) | NULL | 失败时所在的步骤 |
| `retry_count` | TINYINT UNSIGNED | NOT NULL, DEFAULT 0 | 已重试次数 |
| `priority` | TINYINT UNSIGNED | NOT NULL, DEFAULT 5 | 任务优先级 1(highest)~10(lowest) |
| `redis_progress_key` | VARCHAR(100) | NULL | Redis 中存储实时进度的 Key |
| `created_at` | DATETIME(3) | NOT NULL, DEFAULT CURRENT_TIMESTAMP(3) | 创建时间 |
| `updated_at` | DATETIME(3) | NOT NULL, DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE | 更新时间 |
| `completed_at` | DATETIME(3) | NULL | 完成时间 |

**索引设计：**

| 索引名 | 类型 | 字段 | 说明 |
|--------|------|------|------|
| `pk_id` | PRIMARY | id | 主键 |
| `uk_biz_id` | UNIQUE | biz_id | 业务主键唯一 |
| `uk_task_id` | UNIQUE | task_id | 任务 ID 唯一索引 |
| `idx_source_video_biz` | BTREE | source_video_biz_id | 按拆解视频素材查询任务 |
| `idx_status_priority` | COMPOSITE | (status, priority) | 消费者轮询队列：按状态+优先级排序 |
| `idx_created_at` | BTREE | created_at | 按创建时间排序 |
| `idx_status_updated` | COMPOSITE | (status, updated_at) | 查询超时未完成的任务 |

**DDL 语句：**

```sql
CREATE TABLE video_analysis_task (
    id              BIGINT UNSIGNED AUTO_INCREMENT,
    biz_id          BIGINT UNSIGNED NOT NULL,
    task_id         VARCHAR(36)    NOT NULL,
    source_video_biz_id BIGINT UNSIGNED NOT NULL,
    status          VARCHAR(20)    NOT NULL DEFAULT 'PENDING',
    progress        TINYINT UNSIGNED NOT NULL DEFAULT 0,
    progress_step   VARCHAR(50)    NULL,
    source_file_path VARCHAR(500)  NOT NULL,
    file_size       BIGINT UNSIGNED NULL,
    error_message   TEXT           NULL,
    error_step      VARCHAR(50)    NULL,
    retry_count     TINYINT UNSIGNED NOT NULL DEFAULT 0,
    priority        TINYINT UNSIGNED NOT NULL DEFAULT 5,
    redis_progress_key VARCHAR(100) NULL,
    created_at      DATETIME(3)    NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
    updated_at      DATETIME(3)    NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
    completed_at    DATETIME(3)    NULL,

    CONSTRAINT pk_video_analysis_task PRIMARY KEY (id),
    CONSTRAINT uk_video_analysis_task_biz_id UNIQUE (biz_id),
    CONSTRAINT uk_video_analysis_task_id UNIQUE (task_id),
    CONSTRAINT fk_task_source_video FOREIGN KEY (source_video_biz_id) REFERENCES analysis_video_material(biz_id)
        ON DELETE RESTRICT ON UPDATE CASCADE,
    CONSTRAINT chk_progress_range CHECK (progress >= 0 AND progress <= 100),
    CONSTRAINT chk_status_values CHECK (status IN ('PENDING','PROCESSING','ANALYZING','COMPLETED','FAILED','CANCELED')),
    CONSTRAINT chk_priority_range CHECK (priority >= 1 AND priority <= 10),
    CONSTRAINT chk_retry_max CHECK (retry_count <= 3)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;

CREATE INDEX idx_task_status_priority ON video_analysis_task (status, priority);
CREATE INDEX idx_task_created_at ON video_analysis_task (created_at);
CREATE INDEX idx_task_status_updated ON video_analysis_task (status, updated_at);
CREATE INDEX idx_task_source_video_biz ON video_analysis_task (source_video_biz_id);
```

**P0 状态约束：**
- `CANCELED` 只允许从 `PENDING` 进入（尚未被消费者处理）
- `DELETE` 不是状态值，表示接口层对历史记录执行删除动作
- `FAILED` 任务可进入 `retry` 流程（`retry_count <= 3`）

**P0 批量上传建模约束：**
- `POST /videos/upload/batch` 返回 `taskIds[]`，每条视频创建独立 `video_analysis_task` 记录
- P0 不新增 `video_analysis_source` 子表，避免 `shot/asr_segment/key_frame` 的联合主键冲突
- 多样例融合统一在模板提取阶段处理（`video_structure_template.source_task_ids`）

### 4.2.2 shot（镜头切分结果）

| 字段名 | 数据类型 | 约束 | 说明 |
|--------|----------|------|------|
| `id` | BIGINT UNSIGNED | PK, AUTO_INCREMENT | 主键 |
| `task_id` | VARCHAR(36) | FK, NOT NULL | 关联拆解任务 |
| `shot_index` | SMALLINT UNSIGNED | NOT NULL | 镜头序号 (从 0 开始) |
| `start_time` | DECIMAL(10,3) | NOT NULL | 起始时间（秒） |
| `end_time` | DECIMAL(10,3) | NOT NULL | 结束时间（秒） |
| `duration` | DECIMAL(10,3) | NOT NULL | 持续时长（秒） |
| `scene_score` | DECIMAL(4,3) | NULL | 帧间差异值 0.000~1.000 |
| `thumbnail_path` | VARCHAR(500) | NULL | 镜头缩略图路径 |
| `shot_type` | VARCHAR(30) | NULL | LLM 分类的镜头类型 |
| `description` | VARCHAR(500) | NULL | LLM 生成的镜头描述 |
| `created_at` | DATETIME(3) | NOT NULL, DEFAULT CURRENT_TIMESTAMP(3) | 创建时间 |

**索引设计：**

| 索引名 | 类型 | 字段 | 说明 |
|--------|------|------|------|
| `pk_shot` | PRIMARY | id | 主键 |
| `uk_task_shot` | UNIQUE | (task_id, shot_index) | 同一任务内镜头序号唯一 |
| `idx_shot_task` | BTREE | task_id | 按任务查询所有镜头 |
| `idx_shot_score` | BTREE | (task_id, scene_score DESC) | Hook 锁定抽帧：按 sceneScore 降序排序 |

**DDL 语句：**

```sql
CREATE TABLE shot (
    id              BIGINT UNSIGNED AUTO_INCREMENT,
    task_id         VARCHAR(36)    NOT NULL,
    shot_index      SMALLINT UNSIGNED NOT NULL,
    start_time      DECIMAL(10,3)  NOT NULL,
    end_time        DECIMAL(10,3)  NOT NULL,
    duration        DECIMAL(10,3)  NOT NULL,
    scene_score     DECIMAL(4,3)   NULL,
    thumbnail_path  VARCHAR(500)   NULL,
    shot_type       VARCHAR(30)    NULL,
    description     VARCHAR(500)   NULL,
    created_at      DATETIME(3)    NOT NULL DEFAULT CURRENT_TIMESTAMP(3),

    CONSTRAINT pk_shot PRIMARY KEY (id),
    CONSTRAINT uk_task_shot UNIQUE (task_id, shot_index),
    CONSTRAINT fk_shot_task FOREIGN KEY (task_id) REFERENCES video_analysis_task(task_id)
        ON DELETE CASCADE ON UPDATE CASCADE,
    CONSTRAINT chk_shot_time CHECK (end_time > start_time)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;

CREATE INDEX idx_shot_score ON shot (task_id, scene_score DESC);
```

## 4.5 扩展性设计要点

### 4.5.1 JSON 字段策略

以下字段使用 MySQL JSON 类型而非拆分为独立子表，原因：

| 字段 | 表 | JSON 原因 |
|------|------|-----------|
| video_info | analysis_result_core（结构化字段） | 高频展示改为结构化列，避免 JSON 热读 |
| script_structure | analysis_result_timeline_asset / video_structure_template | 嵌套层级深、仅按需加载 |
| rhythm_structure | 同上 | LLM 输出格式随 Prompt 迭代可能变化 |
| packaging_structure | 同上 | 包装元素多样性高 |
| category_extensions | video_structure_template | 核心动态性——每个品类字段完全不同 |
| viral_factors | video_structure_template | 因子列表数量动态变化 |
| dynamic_fields | category_knowledge | KV 矩阵的核心，无预定义结构约束 |
| prompt_overrides | category_knowledge | 文本策略，长度不定 |
| composed_timeline | migration_task | 时间线编排结果结构复杂可嵌套 |
| gaps / required_slots / filled_slots | gap_analysis | 槽位结构动态变化 |

> [!TIP]
> MySQL 5.7+ 原生支持 JSON 索引（`CREATE INDEX ... ON table ((CAST(json_field->>'$.key' AS CHAR(50))))`）。对于高频查询的 JSON 内部字段（如 `dynamicExtensionFields` 中的 `fieldName`），可在数据量增长后按需建立虚拟列索引。

### 4.5.2 分库分表预留

| 维度 | 表 | 分片键 | 触发条件 |
|------|------|--------|----------|
| 任务维度 | video_analysis_task / shot / asr_segment / key_frame / timeline_event / analysis_result_core / analysis_result_text_asset / analysis_result_timeline_asset | biz_id Hash | 单表 > 1000 万行 |
| 模板维度 | video_structure_template / template_shot / viral_factor | biz_id Hash | 品类 > 100 个 |
| 用户维度 | creative_material / migration_task / migration_material / gap_analysis | biz_id/migration_id Hash | 用户量 > 10 万 |

### 4.5.3 软删除策略

核心业务表（video_structure_template、category_knowledge、analysis_video_material、creative_material）采用 `status` 字段实现软删除：
- `template.status = 'ARCHIVED'` 表示归档（不物理删除，迁移任务可能仍在引用）
- `analysis_video_material.status = 'DELETED'` 表示拆解素材逻辑删除
- `creative_material.status = 'DELETED'` 表示创作素材逻辑删除
- `category_knowledge.review_status = 'REJECTED'` 表示审核拒绝（保留记录避免重复注册）

### 4.5.4 一致性保证

| 场景 | 策略 |
|------|------|
| 任务状态更新 + 进度刷新 | 使用 Redis 作为实时进度缓存，MySQL 作为最终持久化；通过 MQ 消费者写入 MySQL |
| 品类热注册并发冲突 | `category_id` 唯一索引 + `INSERT ... ON DUPLICATE KEY UPDATE` 实现幂等 |
| 模板与品类的引用一致性 | `FK ... ON DELETE RESTRICT` 阻止删除仍有模板引用的品类 |
| analysis_result 三层表与 task 一一对应 | `task_id` 唯一索引保证 |
